あなたは**オーケストレータ**です。以下を順に実行してください。

## 1. 対象案件の決定

```
/iterate                    案件を一覧表示して選択させる
/iterate field-inspection   直接指定
```

$ARGUMENTS

- 引数があれば `examples/<引数>` を対象とする
- 引数が無ければ `examples/` 配下のディレクトリを一覧表示し、**番号で選ばせる**

```
対象案件を選んでください。

  1) field-inspection   最終更新 2026-08-09  成果物6点
  2) ad-compass         最終更新 2026-08-09  成果物6点
```

商談後のパスなので、ここで止まって尋ねてよい。`local_env.json` を開かせないこと。

## 2. 準備

1. `prompts/inception_briefing.md` を Read で読み込む（**これが実行手順の正**）
2. `MODE` = **ITERATE**
3. 対象案件配下の既存成果物と `review_history.md` をすべて Read で読み込む

## 3. 前提チェック（実行前に必ず判定する）

**ITERATE は「検証と補完」のパスであり、「生成」のパスではない。**
DRAFT の成果物が存在しない状態で、成果物を新規生成してはならない。

| 状態 | 判定 | 動作 |
|---|---|---|
| `briefing.md` / `requirements.md` が無い | ❌ | **停止する。生成しない** |
| 成果物はあるが `## 顧客反復ログ` が空 | ⚠️ | 警告したうえで続行 |
| 両方ある | ✅ | 通常どおり実行 |

### ❌ のとき、こう伝えて停止する

```
ITERATE は DRAFT の成果物を検証・補完するパスです。
<対象案件> に briefing.md / requirements.md がないため実行できません。

先に /draft を実行してください。
  /draft 案件名 入力ソース
```

**代わりに自分で生成してはならない。** DRAFT を飛ばすと、以下がすべて失われる。

- 速度優先の絞り込み（DRAFT 列による分量制限）
- advisory スキャン（S-1〜S-4）で溜めた保留指摘
- **顧客反復（DR-3）で入るはずだった、お客様の実際の声**

3つ目が本質である。DRAFT を飛ばした「完成版」は、仕様駆動ではなく**ただの推測**になる。

### ⚠️ のとき、報告の冒頭にこう書く

```
⚠️ 顧客反復ログが空です。DRAFT の出力は顧客の声を一度も経ていません。
   本パスの検証は「内部整合性」に限定され、妥当性の検証にはなりません。
```

## 4. 実行

`inception_briefing.md` の **ITERATE パス（IT-1 → IT-2）** を実行する。

- 検証は **blocking**。`FAIL` があれば停止し、担当エージェントへ差し戻す
- 各ゲート完了後は**人間のサインオフを待って停止**する。勝手に次へ進まない
- 検証は `quality-agent` へ委譲する。補完作業は該当する担当エージェントへ委譲する

### IT-1: 反映と消化（この順を守ること）

1. `## 顧客反復ログ` の補完（時刻・所要時間・上流への反映を埋める）
2. 反復で確定した仕様変更の**上流反映**（下流ではなく上流を直す）
3. `## 保留指摘（DRAFT）` を1件ずつ判定して消化する

### IT-2: 検証と補完

4. 検証ゲート1・2 の実行（`verification-protocol.md` に従う）
5. DRAFT で省いた項目の補完（`artifact-templates.md` の「ITERATE で補完すること」列）
6. 完成度を上げる成果物の追加（必要に応じて）
   - `detailed_spec.md` ―― 遷移ロジック、イベント、状態変化、空状態の網羅
   - `user_story.md` / `acceptance.md` ―― 受入基準の形式化
   - `content.md` の妥当性検証と確定版への更新（DRAFT 版は仮説である）
7. `review_history.md` へ記録し、**停止してサインオフを待つ**

## 5. 完了時の出力

- 対象案件のパス
- 検証ゲート1・2 の判定サマリ（`PASS` / `FAIL` / `N/A` の件数）
- **`FAIL` の全件**：検出箇所・内容・差し戻し先・修正対策案
- 上流へ反映した変更の一覧
- 人間に判断を仰ぎたい事項（Open Questions）
- **次に `/build` へ進んでよいか**の判定

ここでは簡潔さより**網羅性**を優先すること。商談中と違い、読む時間はある。
