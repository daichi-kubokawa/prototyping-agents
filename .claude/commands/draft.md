### 引数の解決（引数は `local_env.json` より優先）

引数は最大2つ。**`<案件名> <入力ソース>`** の順に解釈する。

| 引数 | 解釈 |
|---|---|
| 第1引数 | **案件名**。ここから `OUTPUT_DIR` を導出する |
| 第2引数以降 | **入力ソース**（下表で自動判別） |

**`OUTPUT_DIR` の導出**

- 第1引数が半角英小文字・数字・ハイフンのみ → `examples/<第1引数>` をそのまま使う
- 第1引数が日本語等を含む → **内容から適切な英小文字スラッグを生成**する
  （例: `設備点検アプリ` → `examples/field-inspection`）
- **導出したパスは、必ず報告の冒頭で1行明示する**（意図しない場所への書き出しを防ぐため）
- 第1引数が無い → `local_env.json` の `OUTPUT_DIR` を使う

**入力ソースの自動判別**

| 形 | 解釈 |
|---|---|
| `http://` / `https://` で始まる | `FIGJAM_URL` として Figma MCP で取得 |
| `@` で始まる | ファイルパス。Read して `RAW_HEARING_MEMO` とする |
| それ以外のテキスト | そのまま `RAW_HEARING_MEMO` とする |
| 指定なし | `local_env.json` の `FIGJAM_URL` → 失敗時 `RAW_HEARING_MEMO` |

`PROJECT_NAME` / `PROJECT_SUMMARY` は、引数の案件名と入力ソースから補って構わない。
不足しても実行を止めないこと。

外部整理ツール（NotebookLM 等）の出力を渡された場合は、
`.claude/knowledge/product-agent/hearing-inputs.md` の「取り込み方」に従い、
**二次情報である旨を `briefing.md` の Assumptions に明記**する。

## 1-c. 既存成果物の扱い（**聞かずに判定する**）

対象ディレクトリに既存の成果物があるかで挙動を変える。
**商談中である。人間に問い返して止まってはならない。**

| 状態 | モード | 動作 |
|---|---|---|
| 成果物なし | **新規** | ゼロから生成（DR-1 から） |
| `briefing.md` が存在する | **継続** | 前回を読み、**差分だけを更新する** |

### 継続モードの手順

1. 既存の `briefing` / `requirements` / `design` / `screens` / `content` / `Guidelines` を Read する
2. 新しい入力（FigJam / メモ）との差分を判定する
   - **新しく判明した事実** → 該当セクションを更新
   - **前回と矛盾する内容** → 新しい方を採用し、`review_history.md` に変更として記録
   - **変化がない箇所** → **触らない。再生成しない**
3. 前回の **Open Questions のうち、今回解消したもの**を消し、新たに出たものを追加する
4. `review_history.md` に `## 第n回商談` を追加し、その回で変わったことを記録する

> ⚠️ **全部作り直してはならない。**
> 変わっていない箇所を再生成すると、**前回お客様と合意した表現が理由なく変わる。**
> それは信頼を損ない、「前回と言ってることが違う」という指摘を招く。
>
> 「作り直したい」場合は、別の案件名で実行すればよい。

継続モードのとき、報告の冒頭に **`継続（第n回）`** と明示すること。

## 2. 実行

`inception_briefing.md` の **DRAFT パス（DR-1 → DR-2 → DR-3）** を実行する。

- **委譲は2回だけ。** `product-agent` に1回（`briefing` → `requirements`）、
  `design-agent` に1回（`design` → `screens`/`content` → `Guidelines` → `figma_make_prompt`）。
  **成果物ごとに呼び直さない。** 委譲1回あたり約1〜3分のコールドスタートが乗る
- 委譲時は、`artifact-templates.md` / `requirements-template.md` の
  **DRAFT 列と行数の目安を必ず本文に書いて渡す**。渡さないと完全版の構成で書かれる
- `product-agent` が返ったら、**`design-agent` へ渡す前に** S-5 を実行する
  （上流で直せば1箇所で済む）
- **一切停止しない。** 確認を求めず、承認を待たず、DR-2 の完了まで走り切る
- 検証は **advisory**。`FAIL` は `review_history.md` の `## 保留指摘（DRAFT）` へ追記して次へ進む。差し戻しも再生成もしない
- `FIGJAM_URL` の MCP 接続は **2回失敗したら即座に `RAW_HEARING_MEMO` へフォールバック**する。接続で粘らない
- C-3（装置）／C-4（物理環境）が欠けていたら、推測で埋めて Open Questions に記録し、進む

### 進行を止めずに警告する3つ

以下だけは、報告の**冒頭に1行**で警告する（ただし進行は止めない）。

1. 機密情報が平文で混入している
2. `innerHTML` 系の危険なバインドが設計に混入している
3. 利用文脈 C-3 または C-4 が**完全に**欠落している

## 3-b. 回収先ディレクトリの自動生成（省略不可）

成果物の生成が終わったら、**商談後に Figma Make の出力を入れる箱を先に作っておく。**
空のまま終わってもよい。**空であること自体が「未回収」という記録になる。**

1. 連番 `NN` を決める ―― 新規なら `01`、継続なら `第n回` に合わせてゼロ埋め2桁
2. 日付を `date +%Y-%m-%d` で取得する
3. `<OUTPUT_DIR>/figma_output/<NN>_<日付>/` を作成する
4. そのディレクトリに以下の2ファイルを置く

`README.md`

```markdown
# 回収手順（このディレクトリに Figma Make の出力を入れる）

1. Figma Make の **Code** 表示 → **右上のダウンロードアイコン** → zip を取得
   （左隣はコード整形。押し間違えないこと）
2. 展開したプロジェクトフォルダごと、このディレクトリの直下に置く
   ―― `node_modules` / `dist` / ロックファイル / zip 本体は残さない
3. 置いたら、下の3つを実行して照合できる状態か確かめる

    grep -r "<content.md の表示文字列の一部>" .
    python3 ../../../../scripts/check_forbidden.py .
    python3 ../../../../scripts/check_upload_safety.py ./<プロジェクト名>/src/imports/

**空のまま `/iterate` を実行した場合**、「伝票のみを根拠に仕様を更新した」と記録され、
画面と仕様のズレは埋まらないまま次の商談に入ることになる。
```

**作成は1回だけ。** 既に同名ディレクトリがあれば何もしない（上書き禁止）。
