# 成果物テンプレート（design-agent）

---

## 1. Mini-ADR 形式（`design.md` の中核）

**D-01 と D-02 は必須。** 欠落した成果物は quality-agent の検証ゲートで差し戻される。

```markdown
### 設計判断 D-01: 輝度極性の決定

- **決定**: 〈Light / Dark / 両極性対応〉を採用する。
- **根拠となる利用文脈**: requirements.md「§1 ペルソナと利用文脈」C-4 より
  〈引用した具体的な文脈記述〉
- **導出プロセス**: 決定モデル①の Step〈n〉分岐〈X〉に該当。
  加点評価の内訳：Light 側〈…〉／Dark 側〈…〉。
- **棄却した選択肢とその理由**: 〈逆の極性を採らなかった理由を、文脈変数に基づいて記述〉
- **この決定が崩れる条件（再検討トリガ）**: 〈利用文脈がどう変化したら見直すべきか〉
```

```markdown
### 設計判断 D-02: 操作アンカー位置の決定

- **決定**: 〈下端アンカー / 上端 / サイド / 中央 / 非固定〉を採用する。
- **根拠となる身体的制約**: requirements.md C-3 より〈把持姿勢・入力方式・画面寸法の引用〉
- **Fitts 法則による評価**: 主要導線〈操作名〉について D を〈…〉に短縮。
  対して破壊的操作〈操作名〉は D を意図的に〈…〉確保。
- **棄却した選択肢とその理由**: 〈…〉
- **この決定が崩れる条件（再検討トリガ）**: 〈…〉
```

情報設計・画面構成は **D-03**、技術構成は **D-04** として、同形式の ADR で記録する。

## 2. `design.md` の構成

> ⚠️ **DRAFT パスでは「DRAFT」列が ✅ の節だけを書く。**
> それ以外は**見出しだけ置いて「ITERATE パスで記述」と一行**書き、中身を書いてはならない。
> DRAFT の目的は速度であり、完全性ではない。**書きすぎは仕様違反である。**
>
> **DRAFT 時の分量目安: 全体で 60行以内。**

| § | 節 | DRAFT |
|---|---|---|
| 0 | **設計判断 D-00: 支配的な設計判断の特定** | ✅ **必須・最初に書く** |
| 1 | 利用文脈サマリ（C-1〜C-5 の要約） | ✅ 3行以内 |
| 2 | **設計判断 D-01: 輝度極性** | ✅ **必須・全項目** |
| 3 | **設計判断 D-02: 操作アンカー位置** | ✅ **必須・全項目** |
| 4 | 設計判断 D-03: 情報設計・画面構成 ／ D-04: 技術構成 | — |
| 5 | 中核ドメインロジックのインターフェースと例外制御フロー | — |
| 6 | セキュリティ設計（DOM バインド規約、秘匿情報の保持境界） | — |
| 7 | 状態遷移図（Mermaid `stateDiagram-v2`） | — |
| 8 | アクセシビリティ方針 | — |
| 9 | ユニット分解と依存関係 DAG | — |
| 10 | 未確定の前提（Open Assumptions）と要確認事項 | ✅ 箇条書きのみ |

**§6 を DRAFT で省いても、DOM バインド規約そのものは省略されない。**
規約は `figma_make_prompt.md` の Constraints へ必ず転記されるため、安全性は落ちない。

### 設計判断 D-00: 支配的な設計判断の特定（必ず最初に書く）

**用意された決定モデルを機械的に全部回してはならない。**
まず「この案件で勝負を決める判断は何か」を宣言し、**支配的なものにだけ深く踏み込む**。

```markdown
## 設計判断 D-00: 支配的な設計判断の特定

- **支配的な判断**: 〈身体的制約 / 情報設計・認知負荷 / その他〉
- **根拠**: requirements.md 〈C-n〉より〈引用〉
- **各モデルの適用可否**:
  - D-01 輝度極性: 〈支配的 / 準支配的 / **非支配的**〉 — 〈1文の理由〉
  - D-02 操作アンカー: 〈同上〉
  - D-03 情報設計・認知負荷: 〈同上〉
- **`screens.md` の要否**: 〈要 / 不要〉 — 〈画面数と理由〉
- **`content.md` の要否**: 〈要 / 不要〉 — **コンテンツ駆動型か**
  （画面から文字を全部消したとき、製品として何も残らないなら「要」）
```

**「非支配的」と判定したモデルは、フル ADR を書かない。**
「既定として〈Light〉を採用。制約が無いため論証は不要」の1〜2行で済ませる。
情報が無いところから1節かけて結論を出すのは、導出ではなく儀式である。

**判定の目安**

| 支配的なもの | 兆候（requirements.md に現れる） | 深掘りすべきモデル |
|---|---|---|
| **身体的制約** | 環境照度・把持姿勢・手袋・移動・騒音の記述がある | D-01 / D-02 |
| **情報設計・認知負荷** | 認知的余力の低下、判断の分岐、心理的障壁、複数画面 | D-03 ＋ `screens.md` |

### ADR 番号の割り当て（固定・取り違え禁止）

| 番号 | 対象 | 由来する決定モデル |
|---|---|---|
| **D-01** | 輝度極性（Light / Dark） | モデル① |
| **D-02** | 操作アンカー位置 | モデル②（Fitts） |
| **D-03** | **情報設計・画面構成** | ―（`screens.md` と対で扱う） |
| **D-04** | 技術構成 | モデル③ |

**モデル番号と ADR 番号は一致しない。** モデル③は D-04 である。
過去に D-03 を技術構成の意味でも使っていたため、同一文書内で2つの意味を持つ事故が発生した。
**この表を正とする。**

なお実装は本フレームワークの範囲外であるため、**D-04 は「引き渡し時の推奨構成」**であり、
実装側を拘束しない。
| **コンテンツそのもの** | 「基準を見せる」「手順を案内する」「情報を比較させる」 | ＋ `content.md`（実文言） |
| どちらも弱い | 制約の記述が乏しい | 既定値で処理し、Open Questions を厚くする |

## 2-b. `screens.md` / `content.md`（条件付き成果物）

D-00 で「要」と判定したときのみ作成する。
書式と導出手順は `.claude/knowledge/design-agent/screen-specification.md` に従う。

| 成果物 | 中身 | 無いとどうなるか |
|---|---|---|
| `screens.md` | 画面一覧／遷移図（Mermaid）／表示要素／アクション／**空状態と条件分岐** | Elements 節が書けない。正常系だけのプロトタイプになる |
| `content.md` | **実際に画面へ出る文言そのもの** | Figma Make がダミーテキストで埋め、製品として何も伝わらない |

Elements は「`screens.md` の表示要素 × `content.md` の文言 × `Guidelines.md` のトークン」で構成される。
どれが欠けても、その分だけ生成側の推測で埋まる。

## 3. `Guidelines.md` の構成

> ⚠️ **DRAFT 時の分量目安: 全体で 80行以内。**
> ✅ の節も**トークンの値と一行の根拠だけ**を書く。論証・解説は ITERATE パスで足す。

| § | 節 | DRAFT |
|---|---|---|
| 1 | 禁則事項 P-1〜P-6 の転記 | — （`figma_make_prompt.md` が転記する） |
| 2 | カラートークン＋**コントラスト比の実測値** | ✅ 最小セット（背景／前景2段／境界／アクセント1色）。**下記の表形式は必須**（検算スクリプトが読む） |
| 3 | タイポグラフィ | ✅ 書体スタックとサイズ3段階のみ。**選定理由は1文** |
| 4 | スペーシングとレイアウトグリッド | ✅ スケール＋**群内／群間の2値を明示**（近接／省略不可）。密度の論証は ITERATE |
| 5 | コンポーネント規約 | ✅ 主要導線のターゲット寸法。**高さと最小幅の両方**（省略不可） |
| 6 | モーション規約 | — |
| 7 | **変更要求 → トークン写像表** | ✅ **必須**（DR-3 の反復速度を決めるため） |
| 8 | 禁止識別子リスト | — （`figma_make_prompt.md` が転記する） |

### ターゲット寸法は高さと最小幅の両方を書く

**高さだけを定義してはならない。** 日本語は文字単位で折り返すため、
幅が不足したラベルは**1文字ずつ縦に積まれて溢れる**。欧文は単語単位で折り返すため起きにくく、
テンプレートを英語圏の感覚で書くと必ず抜ける。

```
| `--target-primary`  | 高さ 40px ／ 最小幅 96px | 主要導線 |
| `--target-choice`   | 高さ 36px ／ 最小幅 72px | 選択肢（「その他」で3文字ぶん＋余白） |
```

最小幅は**そのラベルの最長文字数から逆算する**。文字数は `content.md` を見れば分かる。

**最小幅の指定だけでは足りない。** flex で横並びにした要素は既定で縮むため、
`flex-shrink: 0` を併記させること。実際に、幅の下限も縮み止めも無いボタンが
親の都合で圧縮され、「メ／ー／ル」と縦に積まれて溢れた事例が発生している。

### カラートークン表の形式（機械可読・形式固定）

`Guidelines.md` の §2 は**必ず以下の5列**で書く。列を増減させたり、比率を文中に散らしてはならない。
`scripts/check_contrast.py` がこの表を読み、WCAG 相対輝度から比率を**再計算**して申告値と照合する。

```markdown
| トークン | 値 | 対比相手 | 比率 | 要求 |
|---|---|---|---|---|
| `--bg` | `#0B0B0C` | — | — | — |
| `--fg` | `#F2F2F2` | `--bg` | — | 4.5:1 |
| `--border` | `#6A6A70` | `--bg` | — | 3.0:1 |
```

- **対比相手**：比較対象のトークン名。基準面そのものには `—` を入れる
- **比率**：**書かない。`—` のままにする。** スクリプトが計算して埋める。
  WCAG の相対輝度はガンマ補正を含む計算であり、**暗算させると遅く、かつ間違える**。
  算術を書き手から取り上げることで、誤りと差し戻しの両方が消える
- **要求**：本文 `4.5:1` ／ 非テキスト `3.0:1`（WCAG 1.4.11）。
  C-1（視力）や C-4（照度）が厳しい場合は、ここを引き上げてよい。下げてはならない

書いたら必ず実行すること。**これは主観の検証ではなく算術である。**

```
python3 scripts/check_contrast.py examples/<案件名>/Guidelines.md --fix
```

`--fix` は比率を実測値で埋める。**要求を下回っている場合は埋めずに FAIL とする** ――
そのときは色値そのものを変えること。比率の書き換えでは解決しない。

なお同じ検査は Claude Code のフックからも自動で走る。**書いた瞬間に埋まる。**

## 4. `figma_make_prompt.md` の構成

Figma Make の構造（**Task / Context / Elements / Behavior / Constraints**）に準拠する。
**ただし形態は2つあり、D-00 の判定によって選ぶ。**

### 形態A：自己完結型（`screens.md` / `content.md` が無い場合）

トークンとレイアウト規約を**プロンプト内に直接埋め込む**。
Figma Make へのペースト1回で完結し、商談中の操作が最も速い。

### 形態B：ポインタ型（`screens.md` / `content.md` がある場合）

内容が1枚に収まらないため、**プロンプトは「どのファイルを読むか」の指示書**にする。
Figma Make に成果物ファイルをアップロードしたうえで、このプロンプトを貼る。

**`figma_make_prompt.md` には、以下をそのまま生成すること**（`〈…〉` は案件に応じて埋める）。
生成物は**そのまま Figma Make のプロンプト欄に貼れる完成形**でなければならない。

````markdown
## Task

〈対象ユーザー〉が〈状況〉で〈目的〉を果たすための、〈デバイス〉向けプロトタイプ画面を生成してください。
これは実装前の「動作する見た目」であり、本番実装ではありません。
バックエンド連携は不要ですが、**空状態と条件分岐は必ず含めてください**。

## 読むファイルと役割

添付したファイルを、以下の役割で参照してください。

| ファイル | 役割 |
|---|---|
| `screens.md` | **画面構成・遷移・表示要素・アクション・空状態と条件分岐** |
| `content.md` | **画面に表示する実際の文言** |
| `Guidelines.md` | カラートークン・タイポグラフィ・スペーシング・ターゲット寸法 |
| `design.md` | D-01（輝度極性）／D-02（操作アンカー）の根拠 |
| `requirements.md` | 非機能要件・アクセシビリティ到達目標 |

## 優先順位（迷ったときの判断）

1. **何を画面に出すか** → `screens.md` の「表示要素」と「アクション」が最優先
2. **その文言は何か** → `content.md` の記載をそのまま使う
3. **どう見せるか** → `Guidelines.md` のトークンのみを使う
4. **なぜそうなのか** → `design.md` の ADR。**この2つの判断を覆さないこと**
   - D-01 輝度極性: 〈Light / Dark〉
   - D-02 操作アンカー: 〈下端固定 / サイドパネル / …〉

記述が矛盾した場合は、上の番号が小さい方を優先してください。

## 絶対に守ること

### 文言
- 本文テキストは**推測で生成せず、必ず `content.md` の記載をそのまま使用**すること
- **ダミーテキスト・プレースホルダー・ロレムイプサムでの生成を禁止**します
- `content.md` に無い文言が必要になった場合は、**生成せずにその旨を明示**してください

### 表示の分岐
- `screens.md` の「表示の分岐」に従い、**空状態**（データ0件）と
  **条件付き表示**（特定の条件下で出さない要素）を必ず実装してください
- 正常系だけの画面は、動かした瞬間に破綻します

### 構成（階層・近接・整列）
- `screens.md` で `［第1］` が付いた要素を、その画面で**最も強い一要素**として扱ってください。
  強調は**ウェイト・サイズ・字間**で作り、色や影で作らないこと
- `screens.md` の「段階的開示」に挙がった要素は、**初期表示に出さない**でください
- 要素の群は、**群の外側の余白を内側の2倍以上**取って分けてください
- 垂直の軸を1〜2本に絞り、テキスト左端とアイコン中心を揃えてください。
  **間隔にはリズムを付けてよいが、軸は崩さないこと**
- **テキストをコンテナから溢れさせないこと。** 日本語は文字単位で折り返すため、
  選択肢やボタンには `Guidelines.md` の**最小幅**を適用し、あわせて**縮み止め**
  （`flex-shrink: 0`）を指定してください。**ラベルが縦に積まれたら、幅か縮み止めの漏れです**
- **`fieldset` / `legend` に `float` を使わないこと。** 後続の要素が押し出され、
  横並びの選択肢が潰れます。ラベルは通常のブロック要素として配置してください

### 意匠（禁則事項 P-1〜P-6）
- **P-1** 意味を持たない装飾グラデーション背景・根拠なきグロー・既定値のグラスモーフィズムを使わない。
  奥行きは構造と余白で表現する
- **P-2** Inter / Arial / Helvetica（既定値としての）/ Roboto / system-ui を無思考に採用しない。
  `Guidelines.md` が指定する書体を実体名で使う
- **P-3** 角丸・影・境界線を全要素に一括適用しない
- **P-4** 絵文字によるアイコン代替、多色イラストの安易な配置をしない
- **P-5** 意味なく中央揃えされた長文、全要素の等間隔配置を避ける
- **P-6** 彩度の高い色を広面積で使わない。アクセントは面積比で数％以内に限定する

### 実装コードを生成する場合（DOM バインド規約・例外なき禁止）
- `innerHTML` / `outerHTML` / `insertAdjacentHTML` / `document.write` による
  ユーザー入力・外部応答・AI生成テキストの展開を**全面禁止**
- 動的要素は `document.createElement()` で生成し、テキストは `.textContent` 経由でのみバインドする
- URL を解釈する属性（`href` / `src` / `formaction`）は `setAttribute()` で設定し、
  `javascript:` / `data:` スキームを拒否する
- イベントは `addEventListener` のみ。インライン `onclick=`、`eval()`、`new Function()`、
  文字列引数の `setTimeout` を禁止する
- テンプレートリテラルによる HTML 文字列組み立てを禁止する
- フレームワークのエスケープ回避 API（`dangerouslySetInnerHTML`、`v-html` 等）も禁止する

**禁止識別子（grep で検知する）**
```
innerHTML / outerHTML / insertAdjacentHTML / document.write
eval( / new Function( / dangerouslySetInnerHTML / v-html
```

### 秘匿情報
- 実URL・アクセスキー等を出力に含めないこと

## 本プロトタイプの位置づけ

〈`content.md` が DRAFT 版の場合は、次を含める〉

> 表示コンテンツは要件から導出した**仮説**であり、実務上の妥当性は未検証です。
> 次回商談での確認対象であり、確定デザインとして扱わないでください。
````

### 商談中の貼り方（この順を守る）

1. Figma Make に `screens.md` / `content.md` / `Guidelines.md` / `design.md` / `requirements.md` を添付する
2. **`figma_make_prompt.md` の全文をプロンプト欄に貼る**（ファイル添付ではなく本文として貼る）

添付ファイルは「参照される資料」、プロンプト欄は「実行される指示」である。
禁則事項と文言規約を添付側に置くと、読まれずに無視されうる。**指示は必ず本文に置くこと。**

> ⚠️ **`briefing.md` は渡さない。**
> 生のヒアリング内容を含み、外部サービスへ送るべきものではない。
> また下流の成果物にすでに反映済みであり、生成には不要である。

どちらの形態でも、Constraints 節の内容（禁則事項・DOM バインド規約・ダミー禁止）は同一とする。

- **Constraints 節には、禁則事項 P-1〜P-6 と DOM バインド規約を必ず転記する**
- **構成の原則（`aesthetic-guardrails.md` §3 の階層・近接・整列）も転記する。**
  禁則だけを渡すと「やってはいけないことは避けたが、配置は凡庸」な画面になる
  （生成先の AI が AI slop と XSS を再導入することを防ぐため）
