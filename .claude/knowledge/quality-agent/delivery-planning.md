# 実装計画（`tasks.md`）と DoD

> ⚠️ **`tasks.md` は BD-1（顧客反復の収束後）で生成する。**
> DR-2 で生成すると、DR-3 の顧客反復によって仕様が動き、実装時には陳腐化している。
> 本家 AI-DLC でも、これに相当する 2.8 デリバリー計画は Inception の最終ステージに置かれている。

---

## 1. Bolt 分解の5原則

**Bolt**（依存関係で結ばれた実装単位のひとまとまりを、一度に走らせる実行サイクル）の
**個数と内容は、プロジェクトごとに要件と依存関係から導出されるものであり、固定ではない。**

- **① Walking Skeleton を最初の Bolt にする**
  端から端まで貫通する最小構成を最初に立てる。
  層ごとの水平分割（先に全画面、次に全ロジック）は禁止。各 Bolt は**垂直スライス**であること

- **② 依存 DAG の順序に従う**
  後続 Bolt が依存する成果物を、先行 Bolt が必ず産出していること。
  循環依存が生じた場合は、分解単位が誤っている

- **③ 各 Bolt は単独で検証可能であること**
  「次の Bolt が終わらないと確認できない」Bolt は、分解の失敗である

- **④ リスクの高いものを前倒しする**
  技術的不確実性が最も高い要素（外部連携、未検証の前提）を早い Bolt に置き、
  失敗を安く早く発見する

- **⑤ 各 Bolt に DoD を定義する**
  すべての Bolt に、少なくとも以下4観点のチェックリストを付す

## 2. DoD の4観点

| 観点 | 問うこと |
|---|---|
| **機能** | 要件のどの項目を満たしたか。受入基準に対して検証したか |
| **セキュリティ** | 禁止識別子が0件か。秘匿情報のライフサイクル要件を満たすか |
| **UX** | 空状態・エラー状態・長文・低速回線で成立するか。アクセシビリティ目標に達しているか |
| **耐障害性** | 外部依存の失敗時に、設計どおり機能低下で継続するか |

### DoD の書き方

**「実装した」ではなく「何がどうなれば完了か」を、検証可能な文で書く。**

- ❌「フォールバック処理を実装する」
- ✅「API キー未設定の状態で入力を送信したとき、例外を投げずにローカル処理の結果が画面に描画される」

完了条件が主観に依存する時点で、それは完了定義ではない。

## 3. `README.md` の生成規約

`design.md` に記録された ADR を要約し、**なぜその技術構成を選んだのか、何を棄却したのか**を
第三者が読める形で記述する。

**結論を持ち込んではならない。** 「なぜこのフレームワークを見送ったのか」の答えは、`design.md` にしか存在しない。
設計側に ADR が存在しないのであれば、それは README の執筆漏れではなく**設計の欠陥**であり、
V-2（トレーサビリティ断絶）として差し戻すべき事項である。

構成：
1. プロジェクト概要
2. アーキテクチャ意思決定の要約（`design.md` の ADR に由来すること）
3. セキュリティ設計境界（秘匿情報の保持境界、XSS 防御設計）
