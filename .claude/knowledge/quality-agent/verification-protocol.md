# 検証ゲート・プロトコル

検査は意見の表明ではなく、**機械的な照合作業**である。
「良いと思う／悪いと思う」ではなく、「上流の記述と下流の記述が一致しているか」だけを見る。

---

## 1. 判定の3値

| 判定 | 意味 |
|---|---|
| `PASS` | 検査項目を満たしている |
| `FAIL` | 満たしていない。**差し戻し先と修正対策案を必ず併記する** |
| `N/A` | 対象成果物がまだ生成されていない。**存在しないものを欠陥として報告してはならない** |

**判定値が1種類しかないゲートは、通過儀礼である。** 品質ゲートの価値は、通さなかった回数で決まる。

---

## 1-b. モードによるゲートの強度（advisory / blocking）

ゲートの**判定基準は一切変わらない。変わるのは「止まるかどうか」だけ**である。

| | **DRAFT パス（商談中）** | **ITERATE パス（商談後）** |
|---|---|---|
| 強度 | **advisory** | **blocking** |
| `FAIL` を検出したら | `review_history.md` の `## 保留指摘（DRAFT）` へ追記し、**そのまま次へ進む** | 停止し、差し戻す |
| 差し戻し・再生成 | **行わない** | 行う |
| 人間のサインオフ | 待たない | 待つ |

> DRAFT パスの advisory スキャン **S-1〜S-5** の定義は
> `prompts/inception_briefing.md` の **DR-2b** にある。本書では重複させない。
> S-5（アップロード安全性）だけは保留にできない例外である。

### advisory 時の必須の作法

- **緩めてよいのは停止判断だけである。検査そのものを省略してはならない。**
  「時間がないので見なかった」は advisory ではなく、単なる未実施である
- 保留指摘は、ITERATE パスで**1件ずつ判定して消化する**。溜めっぱなしにしてはならない
- ただし以下の3つだけは、**DRAFT でも即座に口頭で警告する**（黙って通してはならない）
  1. 機密情報が平文で混入している
  2. `innerHTML` 系の危険なバインドが設計に混入している
  3. 利用文脈 C-3（装置）または C-4（物理環境）が完全に欠落している

  1と2は事故に直結し、3は後続の設計判断すべてを無効化するため、
  「後で直す」が成立しない。指摘だけ即座に行い、**修正は止めずに進めながら行う**。

### 保留指摘の書式

```markdown
## 保留指摘（DRAFT）

| # | 検出箇所 | 種別 | 内容 | ITERATE での判定 |
|---|---|---|---|---|
| 1 | requirements.md §1 | ゲート1 / 抽出漏れ | C-5 が未記述 | *（未判定）* |
```

## 2. 検証ゲート1（上流ブリーフ ➔ 要件定義への移行前）

> ⚠️ この時点で `design.md` も `Guidelines.md` も存在しない。
> **実装レベルの事項（DOM バインド、タイムアウト制御、配色）を検査対象にしてはならない。**
> 検査すれば必ず「定義されていない」となるが、それは欠陥ではなく単に未生成である。

| 検査項目 | 見るもの |
|---|---|
| 利用文脈の抽出漏れ | C-1〜C-5 が抽出されているか。**特に C-3（装置）と C-4（物理環境）の欠落は重大欠陥** |
| 内部矛盾 | `briefing.md` 内で相互に矛盾する記述がないか |
| 解法の混入 | ヒアリング段階の記述に、技術的解法が「確定事項」として紛れ込んでいないか |
| 機密の混入 | マスクされるべき実データが平文で残っていないか |

## 3. 検証ゲート2（下流仕様・設計の相互整合性）

| # | 検査種別 | 検出すべきもの |
|---|---|---|
| **V-1** | **矛盾（Contradiction）** | 上流が禁止した事項を下流が採用していないか。上流が要求した振る舞いを、下流が別の振る舞いに置き換えていないか |
| **V-2** | **トレーサビリティ断絶** | 設計上の決定が、要件のどの記述に由来するか辿れるか。**由来を持たない設計判断（＝設計者の嗜好）**が混入していないか |
| **V-3** | **孤児成果物（Orphan）** | 要件にあるのに設計されていない項目（下流欠落）／設計にあるのに要件にない項目（スコープクリープ） |
| **V-4** | **用語・値の揺れ** | 同一概念に別名が与えられていないか。同一の寸法・状態名・トークン名が、文書間で異なる値を持っていないか |

### 必須の重点検査項目

- **セキュリティ要件の貫通**
  要件が定めた秘匿情報のライフサイクル要件（破棄タイミング、可視範囲）と矛盾する記述が、
  設計側に**1文字でも**混入していないか。永続化を禁じた要件に対し、
  設計側に永続保存やキャッシュを示唆する記述があれば**即時 FAIL**

- **DOM バインド規約の貫通**
  設計側に `innerHTML` 系の危険なバインド、およびフレームワークのエスケープ回避 API を
  許容する記述が残っていないか。`textContent` / `createElement` 規約と、
  grep 可能な禁止識別子リストが明記されているか

- **設計判断のトレーサビリティ**
  **D-01（輝度極性）と D-02（操作アンカー位置）が、C-1〜C-5 のどの記述に由来するかを照合する。**
  根拠・棄却案・再検討トリガのいずれかが欠落した Mini-ADR は不合格として差し戻す

- **フォールバック経路の一致**
  要件が定めた「外部依存の失敗時の振る舞い」と、設計の状態遷移図・例外制御フローが一致しているか。
  図に現れない失敗経路がないか

## 4. 検証ゲート3（引き渡し前の実物チェック）

**実装は本フレームワークの範囲外である。** 本ゲートが見るのは、回収した Figma Make の出力と、確定した仕様の一致である。

**静的チェックは目視せず、スクリプトの終了コードで判定する。3本とも 0 でなければ FAIL とする。**

```
python3 scripts/check_contrast.py      <案件>/Guidelines.md   WCAG 比率の再計算
python3 scripts/check_forbidden.py     <案件>/                禁止識別子の検出
python3 scripts/check_upload_safety.py <案件>/                外部送信の安全性
```

「ドキュメントに禁止と書いてあるか」と「実物に混入していないか」は別である。
**後者しか品質を保証しない。** ゲート2までは前者、ゲート3は後者を見る。

## 5. 監査証跡の書式

`review_history.md` へ**追記（アペンド）のみ**。既存の記録を上書き・削除してはならない。
誤りが判明した場合は、訂正記録として追記する。

セクション名は以下で固定する（表記の揺れは重複セクションの増殖を招く）。

```
## 保留指摘（DRAFT）
## 顧客反復ログ
## 検証ゲート1: 上流ブリーフ ➔ 要件定義への移行前レビュー
## 検証ゲート2: 下流仕様・設計の相互整合性レビュー
## 検証ゲート3: 引き渡し前の実物チェック
```

### 顧客反復ログの書式

DRAFT 中は**2列だけ**を速記する。記録がスピードを殺してはならない。
残りの列は ITERATE パスで補完する。

```markdown
## 顧客反復ログ

| # | お客様の言葉 | 写像先 | 変更内容 | 所要 | 上流への反映 |
|---|---|---|---|---|---|
| 1 | 「もう少し明るく」 | 背景トークン | 明度を1段上げ（極性は維持） | 1分50秒 | ― |
| 2 | 「押しにくい」 | W / D | ターゲット幅を拡大 | 2分10秒 | requirements.md C-3 に追記 |
```

このログは、**「速さ」を裏づける唯一の証跡**である。仕様書には速度は残らない。
反復回数と所要時間を記録して初めて、プロセスの実効性を数字で示せる。

各セクションには、**検査項目・判定・根拠となる該当箇所の引用・修正対策案**を記録し、
末尾に人間のレビューコメント用プレースホルダーを配置する。
再現性のため、レビュー日時と対象コミットも併記すること。
