# `requirements.md` 構成テンプレート

`〈…〉` は `briefing.md` から導出して埋める箇所。**本テンプレートの例示をそのまま転記してはならない。**

```markdown
# requirements.md — 要件定義書

## 1. ペルソナと利用文脈（Context of Use）
### C-1 ユーザー
〈年齢帯・視力/色覚特性・熟練度・認知的余力〉
### C-2 タスク
〈1セッションの操作時間・入力量・連続注視時間・失敗の可逆性〉
### C-3 装置と入力方式
〈デバイス種別・画面サイズ・入力方式・把持姿勢〉
### C-4 物理環境
〈環境照度・時間帯・騒音・移動の有無〉
### C-5 社会的・組織的環境
〈他者への配慮・ブランド制約・法令/アクセシビリティ要求水準〉

> ⚠️ 本節は design-agent の設計判断 D-01 / D-02 の唯一の入力である。
> 推測で埋めた項目は必ず「§6 Assumptions」に転記すること。

## 2. 認知的・身体的ペイン
〈利用文脈から導かれる、失敗すると致命的になる負荷〉

## 3. MoSCoW 優先順位マトリクス
### Must Have（本イテレーションで必須）
- 〈目的と制約として記述する。技術的解法を書かない〉
### Should Have / Could Have
### Won't Have（今回は対象外 ―― 空欄禁止）

## 4. 中核データ構造
〈プロダクトが正規化して扱うべきデータの論理スキーマ。
  永続化方式ではなく、構造と不変条件（invariant）を規定する〉

## 5. 非機能要件
### 5.1 セキュリティ
〈秘匿情報のライフサイクル要件。「どこに置くか」ではなく
  「いつ消えるべきか」「誰に見えてはならないか」「漏洩時の影響は何か」〉
### 5.2 耐障害性
〈外部依存の失敗時に取るべき振る舞い。停止か、機能低下しての継続か〉
### 5.3 アクセシビリティ
〈C-1 と C-5 から導出した WCAG 到達目標〉

## 6. Assumptions（前提・推測）と Open Questions（要確認事項）
〈briefing.md に存在せず、暫定的に埋めた項目を漏れなく列挙する〉
```

## MoSCoW の運用

- **`Won't Have` を空欄にしてはならない。** 何を作らないかの明示は、何を作るかの明示と同等の価値を持つ
- 各要件には**検証手段**（どうなれば満たしたと言えるか）を併記する。検証できない記述は要件ではなく願望である
- ストーリーは層ごとの水平分割ではなく、端から端まで貫く**垂直スライス**で切る
