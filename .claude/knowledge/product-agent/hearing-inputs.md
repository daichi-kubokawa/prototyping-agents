# ヒアリング入力の経路と注意点

`briefing.md` の入力には3経路ある。**どれを使っても `briefing.md` が SSoT であることは変わらない。**
外部ツールの出力は「整理された素材」であって、SSoT ではない。

| 経路 | 向いている場面 | タイミング |
|---|---|---|
| **① FigJam（MCP）** | 商談中にその場で構造化しながら聴く | DRAFT 中 |
| **② 直接メモ（`$ARGUMENTS`）** | MCP が使えない／短時間のヒアリング | DRAFT 中 |
| **③ NotebookLM 等の外部整理ツール** | 長時間の録音、複数資料、既存 RFP がある案件 | **DRAFT の前** or **DEVELOP 中** |

---

## ③ 外部整理ツール（NotebookLM 等）を使う場合

### 位置づけ

**商談中には使えない。** アップロードと処理に時間がかかるため、リアルタイムの対話には乗らない。使いどころは2つ。

- **DRAFT の前**：事前資料（RFP、既存仕様書、過去の議事録）が大量にある案件で、商談前に下調べする
- **DEVELOP 中**：商談の録音を後から文字起こしして、`briefing.md` を補強する

### ⚠️ 最大のリスク ―― 要約は C-3 / C-4 を捨てる

**要約ツールは「何が欲しいか」を残し、「どんな状況で使うか」を捨てる。**

利用文脈は、たいてい**本題の合間に一度だけ漏れる**。

> 「……まあ、片手がふさがってることが多いんで、そのつもりで」
> 「夜は照明を落としてるんで、明るい画面はつらいですね」

要約器はこれをノイズとして落とす。しかし **C-3（装置・把持姿勢）と C-4（物理環境）はここにしか無い**。
落とされると、下流の D-01（輝度極性）も D-02（操作アンカー）も導出できなくなる。

**対策は2つ。両方やること。**

1. **要約させず、抽出させる。** 「まとめて」ではなく「C-1〜C-5 の軸で拾って」と指示する（下記プロンプト）
2. **要約と生ログの両方を渡す。** 要約だけを `RAW_HEARING_MEMO` にしない

### 外部ツールへ渡すプロンプト

```
この資料から、以下の5つの観点で「実際に語られた表現」を抜き出してください。
要約や言い換えをせず、**発言をそのまま引用**してください。
該当する発言がない観点は「言及なし」と明記してください。勝手に推測して埋めないでください。

1. ユーザー：年齢層、熟練度、そのときの心身の状態（疲労・焦り・並行作業）
2. タスク：1回の操作にかかる時間、入力量、失敗したときのやり直しやすさ
3. 装置と姿勢：使う機器、画面サイズ、**手はどうなっているか**（片手/両手/手袋/何かを持っている）
4. 物理環境：**明るさ**、時間帯、騒音、移動中かどうか
5. 周囲の状況：近くに人がいるか、見られて困るものか、守るべきルールや規定

特に 3 と 4 は、本題の合間に一度だけ触れられることが多いので、
雑談や余談に見える箇所も必ず走査してください。
```

3 と 4 を太字で強調しているのは、そこが落ちやすく、かつ落ちると致命的だからである。

### 取り込み方

外部ツールの出力は `inputs/<slug>-hearing.md` に保存し、`/draft` の引数でファイルを指定する。

```
/draft @inputs/parentsync-hearing.md
```

- **`inputs/` は Git 追跡外**とする。生のヒアリング内容には個人情報が含まれるため
- 外部ツールを経由した場合、`briefing.md` の Assumptions に
  **「本ブリーフは外部要約ツールを経由した二次情報を含む」**と明記する。
  一次情報（生の発言）と二次情報（要約）を混ぜたまま下流へ流さない
- 要約由来の記述で C-1〜C-5 を埋めた場合、その項目は Open Questions にも重ねて記載し、
  次回の商談で口頭確認する対象とする
