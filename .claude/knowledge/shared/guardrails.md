# 共通ガードレール（全エージェント）

すべてのエージェントは、成果物を書き始める前に本ファイルを読み込み、以下を無条件で遵守する。

## 1. 言語規約

思考プロセス（Reasoning）、および出力するすべての Markdown・プロンプトは、洗練された**日本語**で統一する。
技術用語・トークン名・コード識別子は原語のまま用いてよいが、**説明文・見出し・論証は例外なく日本語**とする。

## 2. シークレットの完全遮断

環境設定ファイル（`local_env.json` 等）から読み取った実データ ―― 外部サービスの実URL、アクセスキー、
プライベートパス、個人が特定される生ヒアリング内容 ―― を、成果物へ平文で書き出してはならない。
必ず `[Confidential]` `[FigJam Board (Confidential)]` 等のプレースホルダーへ置換する。

Git 公開時の漏洩リスクを物理的に遮断することが目的であり、「たぶん大丈夫」で通してはならない。

### 第三者の固有名詞を含む場合

競合サービス名・取引先名など、第三者の固有名詞に**評価を伴って**言及する記述
（例：「〈サービス名〉は拡散力は強いが、素直な感情表現がしづらい」）は、
サービス名そのものではなく **その評価がどこの判断か**で扱いを決める。

| 評価の出所 | 扱い |
|---|---|
| 自プロダクトの構想 | 実名のまま記載してよい。競合比較は PRD の正当な構成要素である |
| 顧客のヒアリング由来 | `briefing.md` ごと非公開とする。顧客の競争戦略の開示にあたる |

**匿名化（「サービスA」等への置換）で解決しようとしてはならない。**
分類・強み・弱みが揃っていれば対象は特定可能であり、隠せていないのに
隠したつもりになる状態を作る。伏せるなら記述ごと伏せること。

## 3. 層の厳守（要件と解法の分離）

| 層 | 書くべきもの | 書いてはならないもの |
|---|---|---|
| `requirements.md` | 目的・制約・利用文脈 | 技術的解法 |
| `design.md` | 解法と、その導出根拠 | 根拠のない具体値 |
| `Guidelines.md` | トークンと規約 | 由来不明の数値 |

例：
- ❌「単一 HTML ファイルで実装する」 → ✅「ビルド工程なしで配布でき、開くだけで起動できること」
- ❌「背景をダークテーマにする」 → ✅「環境照度〈…〉下で、同室の他者の睡眠を妨げない発光量であること」
- ❌「入力欄を画面下部に置く」 → ✅「片手把持・親指のみで主要導線を〈…〉秒以内に完了できること」

要件側で解法を固定すると、設計側の ADR が「与えられた答えの追認」に堕し、トレードオフ検討が消滅する。

## 4. ゼロ・ハードコード原則

**再利用層（`.claude/agents/` `.claude/knowledge/` `prompts/`）に、特定プロダクトの具体値
（色値・フォント名・レイアウト形状・技術構成）を書き込んではならない。**

具体値は、案件層の利用文脈を決定モデルに代入した「計算結果」としてのみ出力してよい。
根拠なき具体値は、それ自体が設計上の欠陥である。

## 5. SSoT の遵守と不確実性の可視化

- 上流ドキュメントに存在しない情報を、下流で確定事項として捏造してはならない
- 推測が必要な場合は **Assumptions（前提・推測）** として明示する
- 不足している重要情報は **Open Questions（要確認事項）** として列挙する
- 案件層は、ワークフロー実行時にゼロから生成される。ヒアリング前に置かれた記述は対話の産物ではないため、SSoT を汚染する

## 6. 整合性の優先順位

仕様間で矛盾が生じた場合、以下の序列で解決する。上位を正とし、下位を修正する。

1. `briefing.md` → 2. `requirements.md` → 3. `design.md` → 4. `Guidelines.md`
→ 5. `figma_make_prompt.md` → 6. `tasks.md` → 7. `README.md`

## 7. 越権の禁止

- Task ツールによるサブエージェントの起動を行わない（委譲はオーケストレータの責務）
- ビルド環境の構築、依存パッケージのインストール、コードのコンパイル・実行を勝手に行わない
