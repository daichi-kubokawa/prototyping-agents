# 仕様駆動プロトタイピング基盤

[![verify](https://github.com/daichi-kubokawa/prototyping-agents/actions/workflows/verify.yml/badge.svg)](https://github.com/daichi-kubokawa/prototyping-agents/actions/workflows/verify.yml)

お客様と話しながら、その**対話の最中に**仕様を立ち上げ、そのまま画面まで到達させるための仕組みです。

仕様駆動開発（Spec-Driven Development）の実装のひとつですが、**仕様を作る場所が違います。**
机の上ではなく、お客様の目の前で作ります。

```
ヒアリング → 利用文脈の抽出 → 設計判断 → 画面仕様 → Figma Make 用プロンプト
仕様生成 11分50秒 ／ 人手による操作 30秒 ／ 画面到達まで 約20〜28分
```

---

## なぜ作ったか

はじめはプロンプトを書きためていました。ヒアリング内容を渡せば要件定義が出てくるものを、案件ごとに一枚ずつ。

**答えがプロンプトに埋まってしまう**のが問題でした。「背景はダークテーマ」「入力欄は画面下部」。
ある案件で正解だったものが次の案件へ持ち込まれ、屋外で使うアプリに夜の寝室向けの配色が出てくる。
そこで答えを消し、**導出の手順だけを残しました。**
「暗いからダーク」ではなく「環境照度と暗順応から背景輝度を逆算する」に置き換えています。

次に躓いたのが**検証の置き場所**です。各工程にレビューを挟んでいましたが、商談中には回りません。
レビューするのは自分自身で、そのとき自分はお客様と喋っているからです。
**時間軸をずらせば両立しました。** 商談中は止まらない。検証は商談のあとに回す。

最後に分かったのは、**自分で決めた規約を自分で破っていた**ことです。
消したはずのハードコードは入力側へ移動し、審美規約が可読性を上書きし（境界線 2.52:1／要求は 3:1）、
規約の読み違いが待ち時間を積み上げていました。どれも**計測と自動検査で初めて表面化**しています。

規律は掲げるだけでは守れない。**機械が判定できるものは機械に判定させる** ―― というのが結論です。

## 二層構造

再利用する仕組みと、案件ごとの成果物を分離しています。

```
再利用層  .claude/agents/     3体のエージェント定義
          .claude/knowledge/  方法論（決定モデル・規約・テンプレート）
          .claude/commands/   スラッシュコマンド
          prompts/            ワークフロー定義（実行手順の正）
          scripts/            決定論的な検査

案件層    examples/<案件名>/   実行時にゼロから生成される
```

**再利用層には、具体的な色値もフォント名もレイアウトもありません。** これは欠落ではなく設計です。
すべての具体値は、`requirements.md` の利用文脈を決定モデルに代入した**計算結果**として導出されます。

案件層はヒアリングを始めるまで存在しません。対話の産物でない記述を先に置くと、
それは導出ではなく**コピー**になるためです。

## 二周構造 ―― DRAFT と ITERATE

同じ成果物を2周します。**1周目は速く、2周目は堅く。**

| | **DRAFT** | **ITERATE** |
|---|---|---|
| いつ | 商談中（お客様の目の前） | 商談後（自分の机） |
| 最適化するもの | 画面に到達するまでの時間 | 無矛盾とトレーサビリティ |
| 検証ゲート | advisory ―― 記録するが止まらない | blocking ―― FAIL なら差し戻し |

サインオフする人間は自分自身で、お客様の前では喋っています。レビューは物理的に不可能です。
**ゲートは商談中ではなく、商談と商談の「あいだ」で回すもの**という設計にしました。

ただし**モードが変えてよいのは「止まるかどうか」だけ**です。検査そのものは両方で必ず走ります。

## 使い方

```bash
/preflight   # 商談前の点検（MCP疎通・検査スクリプト・権限）
/draft       # 商談中。止まらずに画面まで走る
/log         # 商談中。お客様の改修依頼を1行で記録する
/iterate     # 商談後。検証と補完
```

`/draft` は **`<案件名> <入力ソース>`** を引数で受け取ります。入力は3経路です。

```bash
/draft 設備点検アプリ https://figma.com/board/xxxxx   # FigJam から
/draft 設備点検アプリ @inputs/hearing.md              # 外部整理ツールの出力から
/draft 設備点検アプリ 屋外で手袋をつけた作業員が…      # その場のメモから
```

お客様の目の前での修正は、感覚ではなく**トークンの操作**へ写像して記録します。

```bash
/log もっと明るく → 背景トークン
```

所要時間は前の記録との差から自動算出されます。**この反復ログが「速さ」の唯一の証跡**です。

> 商談1件を通した流れは **[WORKFLOW.md](WORKFLOW.md)** に図でまとめています。

## Figma Make へ何を渡すか

仕様が画面になる接点です。渡すのは**成果物5点**と、プロンプト本文。

```
screens.md        画面構成・遷移・表示要素・空状態と条件分岐
content.md        画面に表示する実際の文言
Guidelines.md     カラートークン・タイポグラフィ・スペーシング
design.md         設計判断の根拠（なぜこの配色・配置なのか）
requirements.md   非機能要件・アクセシビリティ到達目標
```

**`briefing.md` は渡しません。** 生のヒアリング内容を含み、外部サービスへ送るべきものではないためです。

**`figma_make_prompt.md` は添付せず、全文をプロンプト欄に貼ります。**
添付ファイルは「参照される資料」、プロンプト欄は「実行される指示」です。
禁則事項を添付側に置くと、読まれずに無視されえます。

そのプロンプトには、必ずこの一文が入ります。

> 本文テキストは推測で生成せず、必ず `content.md` の記載をそのまま使用すること。
> **ダミーテキスト・プレースホルダーでの生成を禁止する。**

それらしいダミー文で埋まった画面は、動いていても検証できないためです。

## 3体のエージェント

| エージェント | 役割 | 成果物 |
|---|---|---|
| `product-agent` | プロダクトマネージャー | `briefing.md` / `requirements.md`（利用文脈 C-1〜C-5） |
| `design-agent` | テクニカルリード兼 UX デザイナー | `design.md` / `screens.md` / `content.md` / `Guidelines.md` / `figma_make_prompt.md` |
| `quality-agent` | QA リード兼テクニカルライター | `review_history.md` / `tasks.md` |

3体は決まった記号で受け渡しをします。**この鎖が切れると設計が導出できません。**

```
product-agent        design-agent           quality-agent
C-1〜C-5        →    D-01 輝度極性     →    「D-01 は C のどれに由来？」
（利用文脈）           D-02 操作アンカー        遡れなければ差し戻し
```

「夜は電気をつけられない」という一言（C-4）から、ダークテーマの採用（D-01）が**根拠つきで導出**されます。

ただし決定モデルを機械的に全部回すことはしません。まず **D-00「この案件で勝負を決める判断は何か」**
を特定し、支配的なものにだけ深く踏み込みます。身体的制約が薄いプロダクトでは、
配色より**画面に何を乗せるか**が製品の中身になります。

委譲は**1エージェントにつき1回**です。成果物ごとに呼び直すと、起動時間がそのまま待ち時間になります。

> AWS Labs の [AI-DLC Workflows 2.0](https://github.com/awslabs/aidlc-workflows) のステージ体系とメタデータ仕様に準拠しつつ、
> 11体構成を3体へ集約しています。どの責務をどこへ吸収したかは、各エージェント定義の冒頭にあります。

## 商談後に持ち帰るもの

商談中の画面反復は Figma Make 側で起きるため、**そのままでは仕様側に何も戻りません。**
戻す経路は2本あり、どちらも人が通します。

| 経路 | 中身 | いつ |
|---|---|---|
| `/log` | お客様の言葉と、直そうとした対象 ―― **意図** | その場（3秒） |
| `figma_output/` | Figma Make の出力コード ―― **事実** | 商談後 |

回収先は `/draft` が商談ごとに自動生成し、手順を書いた README を同梱します。

`/iterate` は最初にこの2つを突き合わせます。**伝票に無いのに実物が変わっている箇所が、
記録されなかった手動修正**です。箱が空なら「伝票のみを根拠に更新した」と明記して続行します
―― 忘れたこと自体が記録に残ります。

## 検証を主観に任せない

AI が「WCAG を満たしています」と書いても、それは**自己申告**です。
機械が判定できるものは、機械に判定させます。

| スクリプト | 見るもの |
|---|---|
| `check_no_hardcode.py` | 再利用層の散文に色値・既定書体名が無いか（**最も重大な違反**） |
| `check_contrast.py` | カラートークンから WCAG 相対輝度を**再計算**し、要求値の充足を判定 |
| `check_upload_safety.py` | 外部へ渡すファイルに生の発言・実URL・資格情報が残っていないか |
| `check_forbidden.py` | `innerHTML` 等の禁止識別子とインライン `on*` ハンドラ |

```
python3 scripts/verify_all.py     # 4本まとめて。終了コードで判定する
```

**4本とも push のたびに GitHub Actions で走ります。** 冒頭のバッジがその結果です。
コントラストと禁止識別子は PostToolUse フックからも自動実行されます。
**チェックリストは静かに飛ばされますが、フックは飛ばされません。**

このうち2本は、実際に欠陥を捕まえています。

```
境界線のコントラスト 2.52:1   WCAG 1.4.11 の 3:1 未満。手作業で発見 → 以後は自動化
発言引用の転記 11件           渡さないと決めたファイルの中身が、渡すファイルへ移動していた
```

コントラストの比率は**人が書きません**。色値と要求値だけを書き、スクリプトが埋めます。
暗算させると遅く、かつ間違えるためです。

> 止めるのは**算術で決着がつくものだけ**です。
> 「要件と設計が矛盾していないか」のような判断は、人間のサインオフに残しています。

## 実測値

改善は2回。それぞれ同一の入力で前後を計測しています。

| | 改善前 | 改善後 | |
|---|---:|---:|---|
| ① 制約の置き場所を直した | 21分50秒 | **11分31秒** | ▲47% |
| ② 委譲を6回から2回へ統合 | 17分09秒 | **11分50秒** | ▲31% |

①と②の間で検査と成果物を追加したため、一度17分09秒まで戻っています。**11分31秒と17分09秒は地続きではありません。**

画面到達までの内訳は次のとおりです。

```
仕様生成                      11分50秒   実測
ファイル添付とプロンプト貼付      30秒      実測
Figma Make の生成             7〜15分    同一入力でも変動する
```

**短縮できたのは仕様生成の部分**です。Figma Make の生成時間は外部サービスの都合であり、
こちらでは制御できません。詳細は [WORKFLOW.md](WORKFLOW.md) にあります。

## 実例 ―― `examples/it-helpdesk/`

**ワークフローを実際に1回通した結果そのもの**です。手で整えていません。

```
D-00  支配的な判断 = 情報設計（D-03）。輝度も操作位置も従属する
D-01  輝度極性     = Light（暫定）
D-02  操作アンカー  = 一覧の各行内に常設するインラインアンカー
```

**D-01 と D-02 には「再検討トリガ」が付いています。** C-3（装置）と C-4（物理環境）が
ヒアリングで確定しておらず、Assumption のまま導出したためです。
**分からないことを分かったふりで埋めない**ことを、成果物の側で強制しています。

同じエージェントは、別の利用文脈（消灯後の室内・片手操作）では **Dark・下端固定**を導出します。
配色は選択ではなく、C-4 と C-3 からの計算結果です。

Figma Make が生成したコードは `figma_output/` へ回収済みで、検査は全項目 PASS しています。

## スコープ

範囲は**確定した仕様と、動くプロトタイプまで**です。本実装は含みません。

商談で合意した画面は Figma Make の出力です。それを捨てて別実装を起こすと、
合意した画面と実装物が別々に育ちます。実装可能な単位への分解（`tasks.md`）までを引き渡し資料として作り、
そこから先は受け取る側の開発プロセスに委ねます。

**線を引かないことは、責任範囲を曖昧にすることです。**

## 設計原則

- **文脈が設計を決める。嗜好ではない** ―― 根拠なき具体値は、それ自体が欠陥
- **要件は「何を」、設計は「どう」** ―― 解法を要件に書いた時点でトレードオフ検討は消える
- **凡庸さは中立ではなく失敗** ―― 既定の書体・グラデーション・角丸は「選択の放棄」
- **検証は自己申告にしない** ―― 機械が判定できるものは、機械に判定させる
