# 仕様駆動プロトタイピング基盤

[![verify](https://github.com/daichi-kubokawa/prototyping-agents/actions/workflows/verify.yml/badge.svg)](https://github.com/daichi-kubokawa/prototyping-agents/actions/workflows/verify.yml)

**お客様と話しながら、その場で仕様を立ち上げ、動く画面まで到達させるための仕組みです。**

ヒアリング内容を渡すと、要件・設計判断・画面仕様・配色定義・Figma Make 用プロンプトが
一続きで生成されます。あとはそれを Figma Make に貼るだけです。

```
仕様生成 10〜13分 ／ 人手による操作 30秒 ／ 画面に到達するまで 19〜23分
```

配色やレイアウトは、あらかじめ決めていません。**「夜間・暗い部屋」ならダーク、「屋外・直射日光」ならライト。**
同じ仕組みが、利用状況から毎回ちがう答えを出します。

---

## 使い方

```bash
/preflight   # 商談前の点検（接続・検査・権限）
/draft       # 商談中。止まらずに画面まで走る
/log         # 商談中。お客様の要望を1行で記録する
/iterate     # 商談後。検証と補完
```

`/draft` は案件名と入力ソースを引数で受け取ります。設定ファイルを開く必要はありません。

```bash
/draft 設備点検アプリ https://figma.com/board/xxxxx   # FigJam から
/draft 設備点検アプリ @inputs/hearing.md              # メモファイルから
/draft 設備点検アプリ 屋外で手袋をつけた作業員が…      # その場の口頭から
```

商談中の修正は `/log` で記録します（実測18秒）。仕様書はその場では触りません。

```bash
/log もっと明るく → 背景色
```

> 商談1件を通した流れは **[WORKFLOW.md](WORKFLOW.md)** に図でまとめています。

## 生成されるもの

```
briefing.md            ヒアリングの整理（外部へは渡さない）
requirements.md        要件と、誰がどんな状況で使うか
design.md              設計判断とその根拠
screens.md             画面構成・遷移・空状態
content.md             画面に出る実際の文言
Guidelines.md          配色・書体・余白の定義
figma_make_prompt.md   Figma Make に貼るプロンプト
```

Figma Make へは、`briefing.md` と `figma_make_prompt.md` を除く5ファイルを添付し、`figma_make_prompt.md` の内容を本文に貼ります。
`briefing.md` を渡さないのは、生のヒアリング内容が入っているためです。

---

## 二層構造

```
再利用層   .claude/  prompts/  scripts/     どの案件でも変わらない部分
案件層     examples/<案件名>/                実行時にゼロから生成される
```

**再利用層には具体的な色・フォント・レイアウトを持たせず、案件ごとの利用状況から具体値を導出します。**

案件層はヒアリング後に生成し、事前に案件固有の記述を置かない設計です。

---

## 二周構造 ―― 商談中と商談後で止め方を変える

同じ成果物を2周します。

|                  | **DRAFT**（商談中） | **ITERATE**（商談後） |
| ---------------- | ------------------- | --------------------- |
| 優先するもの     | 画面に到達する速さ  | 矛盾がないこと        |
| 問題を見つけたら | 記録して先へ進む    | 止めて差し戻す        |

検証でサインオフするのは自分自身で、そのとき自分はお客様と喋っています。
**レビューは商談中ではなく、商談と商談の「あいだ」で回すもの**という設計です。

ただし**変えてよいのは「止まるかどうか」だけ**で、検査そのものは両方で必ず走ります。

## 3体のエージェント

|                 | 役割 | 作るもの                                                                             |
| --------------- | ---- | ------------------------------------------------------------------------------------ |
| `product-agent` | 要件 | `briefing.md` / `requirements.md`                                                    |
| `design-agent`  | 設計 | `design.md` / `screens.md` / `content.md` / `Guidelines.md` / `figma_make_prompt.md` |
| `quality-agent` | 検証 | `tasks.md`（引き渡し資料）                                                           |

`review_history.md`（レビュー履歴）は全工程で追記されます。
役割を細かく分けるほど受け渡しが増えて遅くなるため、3体に抑えています。
**呼び出しは1体につき1回**です。成果物ごとに呼び直すと、起動時間がそのまま待ち時間になります。

判断の根拠には ISO 9241-11、WCAG、Fitts の法則、OWASP など既存の標準を参照します。
各知識ファイルには出典を明記し、自作の規約は外部根拠がないことも記録しています。

## 検証を自己申告にしない

AI が「基準を満たしています」と書いても、それは検証ではありません。

| スクリプト               | 見るもの                                                 |
| ------------------------ | -------------------------------------------------------- |
| `check_no_hardcode.py`   | 再利用層に具体的な色やフォント名が書かれていないか       |
| `check_contrast.py`      | 配色のコントラスト比を**計算し直して**基準を満たすか判定 |
| `check_upload_safety.py` | 外部へ渡すファイルに顧客の発言や機密が残っていないか     |
| `check_forbidden.py`     | 生成コードに危険な書き方が混入していないか               |

```
python3 scripts/verify_all.py     # 4本まとめて実行する
```

ファイルを書いた瞬間と、リポジトリへ反映するたびの**2箇所で自動実行**されます。
チェックリストではなく構造で担保しています。冒頭のバッジがその結果です。

このうち2本は、実際に欠陥を捕まえています。

```
配色のコントラスト不足   基準を下回っていた箇所を検出
顧客の発言の転記 11件    渡さないと決めたファイルの中身が、渡すファイルへ移っていた
```

> 止めるのは**計算で決着がつくものだけ**です。
> 「要件と設計が矛盾していないか」のような判断は、人間が確認します。

## 実測値

公開している2案件の実測です。**リポジトリの成果物と対応しています。**

|                        | `helpdesk-app` |  `night-app` |
| ---------------------- | -------------: | -----------: |
| 仕様生成               |   **10分51秒** | **12分55秒** |
| 添付とプロンプト貼付   |           30秒 |         30秒 |
| Figma Make の生成      |       11分34秒 |      5分45秒 |
| **画面に到達するまで** |   **22分55秒** | **19分10秒** |
| 配色                   |  Light（既定） | **Dark**（導出） |

**短縮できたのは仕様生成の部分**です。Figma Make の生成時間は外部サービスの都合で、
同じ入力でも5分45秒〜15分17秒（5回計測）と幅があります。こちらでは変えられません。

改善時には、エージェントの呼び出しを6回から2回へ統合し、
仕様生成時間を17分09秒から11分50秒へ約31%短縮しました。

詳細は [WORKFLOW.md](WORKFLOW.md) にあります。

## 実例 ―― 2案件の対比

同じ仕組みを2つの案件に適用した結果です。

|          | `examples/helpdesk-app/`                 | `examples/night-app/`                  |
| -------- | ---------------------------------------- | -------------------------------------- |
| 利用状況 | 装置と物理環境を聞けていない             | 深夜の当直。22時に照明が落ちる         |
| 配色     | Light（**既定値**と明記）                | **Dark**（利用状況から導出）           |
| 操作位置 | デスクトップ標準配置（上部固定・右上）   | 画面下端に固定し、押せる範囲を拡大     |

**同じ判断基準でも、利用状況が変われば結論も変わります。**
そして**情報が足りなければ、導出したふりをしません。** `helpdesk-app` の Light は
「これは既定値である」と `design.md` に書き、次回商談の確認事項として残しています。

また、要件にない機能は追加せず、判断に必要な情報が不足している場合は推測で埋めず、「未確定」として確認事項に残します。

設計判断には、採用理由だけでなく棄却理由と「この判断が崩れる条件」も記録しています。

---

## 範囲

**確定した仕様と、動くプロトタイプまで**です。本実装は含みません。

商談で合意した画面は Figma Make の出力です。それを捨てて別実装を起こすと二重管理になります。
実装できる単位への分解までを引き渡し資料として作り、そこから先は受け取る側に委ねます。
