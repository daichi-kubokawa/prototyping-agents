# 仕様駆動プロトタイピング基盤

お客様と話しながら、その**対話の最中に**仕様を立ち上げ、そのまま画面まで到達させるための仕組みです。
ヒアリングの内容を入力すると、利用文脈の抽出から設計判断、Figma Make 用プロンプトの生成までが一続きに走ります。

仕様駆動開発（Spec-Driven Development）の実装のひとつですが、**仕様を作る場所が違います。**
机の上ではなく、お客様の目の前で作ります。

プロダクトには依存しません。深夜の暗室で片手操作されるアプリにも、真昼の屋外で手袋越しに触るアプリにも、
**同じエージェントがそれぞれ異なる正解を導出します。**

---

## なぜ作ったか

<!-- ★下書きです。ご自身の言葉に置き換えてください -->

はじめは、プロンプトを書きためていました。ヒアリングの内容を渡せば要件定義が出てくるものを、案件ごとに一枚ずつ。

うまくいかなかったのは、**プロンプトの中に答えが埋まってしまう**ことでした。
「背景はダークテーマ」「入力欄は画面下部」―― ある案件で正解だったものが、そのまま次の案件へ持ち込まれる。
屋外で使うアプリにも、夜の寝室向けの配色が出てくる。プロンプトが特定のプロダクトに癒着していました。

そこで答えを消し、**導出の手順だけを残しました。**
「暗いからダークテーマ」ではなく「環境照度と暗順応の状態から、背景輝度とコントラストを逆算する」。
同じエージェントが、正反対の利用文脈から正反対の答えを出せるようになりました。

もうひとつ作り直したのが、**検証の置き場所**です。
最初は各工程にレビューを挟み、通らなければ次へ進めない設計にしていました。
しかし商談中にそれは回りません。レビューする人間は自分自身で、そのとき自分はお客様と喋っているからです。

速さと堅さは相反するように見えて、**時間軸をずらせば両立しました。**
商談中は止まらない。検証は商談が終わってから、自分の机で回す。

速さは瞬発力ではなく、準備の構造で決まる ―― というのが、作ってみて得た結論です。

## 二層構造

再利用する仕組みと、案件ごとの成果物を分離しています。

```
再利用層  .claude/agents/     3体のエージェント定義
          .claude/knowledge/  方法論（決定モデル・規約・テンプレート）
          .claude/commands/   スラッシュコマンド
          prompts/            ワークフロー定義

案件層    examples/<案件名>/   ★実行時にゼロから生成される
```

**再利用層には、具体的な色値もフォント名もレイアウトも書かれていません。** これは欠落ではなく設計です。
すべての具体値は、`requirements.md` の利用文脈を決定モデルに代入した**計算結果**として導出されます。

案件層は、ヒアリングを始めるまで存在しません。対話の産物でない記述を先に置くと、
それは「導出」ではなく「コピー」になるためです。

## 二周構造 ―― DRAFT と ITERATE

同じ成果物を2周します。**1周目は速く、2周目は堅く。**

| | **DRAFT** | **ITERATE** |
|---|---|---|
| いつ | 商談中（お客様の目の前） | 商談後（自分の机） |
| 最適化するもの | 画面に到達するまでの時間 | 論理的無矛盾とトレーサビリティ |
| 検証ゲート | advisory ―― 記録するが止まらない | blocking ―― FAIL なら差し戻し |
| 目標 | 8分で画面へ | 制限なし |

検証ゲートでサインオフする人間は自分自身で、お客様の前では喋っています。
レビューは物理的に不可能であり、そこで止まるのはお客様の時間を捨てているだけです。
**ゲートは商談中ではなく、商談と商談の「あいだ」で回すもの**という設計です。

## 使い方

> 商談1件を準備から実装まで通した流れは **[WORKFLOW.md](WORKFLOW.md)** に図でまとめています。

```bash
/preflight   # 商談前の点検（MCP疎通・設定・権限）
/draft       # 商談中。止まらずに画面まで走る
/log         # 商談中。お客様の改修依頼を1行で記録する
/iterate     # 商談後。検証と補完（案件は一覧から選択）
/build       # 仕様が固まってから。tasks.md → index.html
```

`/draft` は **`<案件名> <入力ソース>`** を引数で受け取ります。
商談中に設定ファイルを開く必要はありません。

```bash
/draft 設備点検アプリ https://figma.com/board/xxxxx   # FigJam から
/draft 設備点検アプリ @inputs/hearing.md              # 外部整理ツールの出力から
/draft 設備点検アプリ 屋外で手袋をつけた作業員が…      # その場のメモから
```

お客様の目の前での修正は、感覚ではなく**トークンの操作**へ写像して記録します。

```bash
/log もっと明るく → 背景トークン
```

所要時間は前の記録との差から自動で算出されます。**この反復ログが「速さ」の唯一の証跡**です。

## Figma Make へ何を渡すか

仕様が画面になる接点。**案件の性質によって渡し方が変わります。**

| 形態 | いつ | 渡すもの |
|---|---|---|
| **自己完結型** | 1画面で足りる案件 | トークンを埋め込んだプロンプト**1枚**。ペーストして完結 |
| **ポインタ型** | 複数画面・情報設計が主役の案件 | 成果物ファイル一式 ＋ 読む順序を指示するプロンプト |

ポインタ型で渡すのは次の5点です。

```
screens.md        画面構成・遷移・表示要素・空状態と条件分岐
content.md        画面に表示する実際の文言
Guidelines.md     カラートークン・タイポグラフィ・スペーシング
design.md         D-01 / D-02 の根拠（なぜこの配色・配置なのか）
requirements.md   非機能要件・アクセシビリティ到達目標
```

**`briefing.md` は渡しません。** 生のヒアリング内容を含むため、外部サービスへ送るべきものではないからです。
下流の成果物にすでに反映済みで、生成にも不要です。

そして **`figma_make_prompt.md` は添付しません。全文をプロンプト欄に貼ります。**
添付ファイルは「参照される資料」、プロンプト欄は「実行される指示」だからです。
禁則事項や文言規約を添付側に置くと、読まれずに無視されうる。指示は必ず本文に置きます。

そしてプロンプトには、必ずこの一文を含めます。

> 画面に表示する本文テキストは、推測で生成せず、必ず `content.md` の記載をそのまま使用すること。
> **ダミーテキスト・プレースホルダーでの生成を禁止する。**

「基準を見せる」「手順を案内する」ようなプロダクトでは、**中身が空だとプロトタイプとして何も伝わりません**。
それらしいダミー文で埋まった画面は、動いていても検証できないためです。

> 形態の選択と、プロンプトの正確な構成は
> [`artifact-templates.md`](.claude/knowledge/design-agent/artifact-templates.md) が定義しています。

## 3体のエージェント

| エージェント | 役割 | 成果物 |
|---|---|---|
| `product-agent` | プロダクトマネージャー | `requirements.md`（利用文脈 C-1〜C-5、スコープ） |
| `design-agent` | テクニカルリード兼 UX デザイナー | `design.md`（ADR）/ `screens.md` / `content.md` / `Guidelines.md` / `figma_make_prompt.md` |
| `quality-agent` | QA リード兼テクニカルライター | `review_history.md` / `tasks.md` / `README.md` |

3体は決まった記号で受け渡しをします。**この鎖が切れると設計が導出できません。**

```
product-agent        design-agent           quality-agent
C-1〜C-5        →    D-01 輝度極性     →    トレーサビリティ検査
（利用文脈）           D-02 操作アンカー        「D-01/D-02 は C のどれに由来？」
                                              遡れなければ差し戻し
```

たとえば「夜は電気をつけられない」という一言（C-4）から、
ダークテーマの採用（D-01）が**根拠つきで導出**されます。好みで選んではいません。

ただし、決定モデルを機械的に全部回すことはしません。まず **D-00「この案件で勝負を決める判断は何か」**
を特定し、支配的なものにだけ深く踏み込みます。身体的制約が薄いプロダクトでは配色や配置は些末な判断であり、
そこでは**画面に何を乗せるか（`screens.md`）**の方が製品の中身になります。

さらに「基準を見せる」「手順を案内する」ような**コンテンツ駆動型**のプロダクトでは、
画面に出る実際の文言（`content.md`）まで用意し、生成側にダミーテキストを禁じます。
文字を消すと何も残らない製品で中身が空だと、プロトタイプとして何も伝わらないためです。

AWS Labs の [AI-DLC Workflows 2.0](https://github.com/awslabs/aidlc-workflows) のステージ体系とメタデータ仕様に準拠しつつ、
11体構成を3体へ集約しています。どの責務をどこへ吸収したかは、各エージェント定義の冒頭に明記しています。

## 商談後に持ち帰るもの

商談中の画面反復は Figma Make 側で起きるため、**そのままでは仕様側に何も戻りません。**
戻す経路は2本あり、どちらも人が通します。

| 経路 | 中身 | いつ |
|---|---|---|
| `/log` | お客様の言葉と、直そうとした対象 ―― **意図** | その場（3秒） |
| `figma_output/` | Figma Make の最終出力 ―― **事実** | 商談後 |

回収先は `/draft` が**商談ごとに自動生成**します。回収手順を書いた README を同梱してあるので、
帰宅後にそのディレクトリを開けば何をすればよいか分かる状態になっています。

```
examples/<案件名>/figma_output/01_2026-08-20/
├── README.md      回収手順（zip の取り方・置くもの・照合コマンド）
└── .gitignore     node_modules / dist を除外
```

Figma Make の Code 表示から zip でまとめて落とせます。
コードの書き出しが最も精度が高く、トークン値も文言もそのまま照合できます。
スクリーンショットは補助です。公開URLは当てにしません。

`/iterate` は最初にこの2つを突き合わせます。**伝票に無いのに実物が変わっている箇所が、
記録されなかった手動修正**です。**箱が空のまま**なら「伝票のみを根拠に更新した」と明記して続行します
―― 忘れたこと自体が記録に残るようにしています。

## 検証を主観に任せない

AI が「WCAG を満たしています」と書いても、それは**自己申告**です。
このリポジトリでは、機械が判定できるものは機械に判定させます。

```
python3 scripts/check_contrast.py examples/<案件名>/Guidelines.md
python3 scripts/check_forbidden.py examples/<案件名>/
python3 scripts/check_upload_safety.py examples/<案件名>/
```

前者は `Guidelines.md` のカラートークンを読み、**WCAG の相対輝度から比率を再計算**して、
申告値との一致と要求値（本文 4.5:1 ／ 非テキスト 3.0:1）の充足を判定します。
後者は `innerHTML` などの禁止識別子とインライン `on*` ハンドラを検出します。
どちらも終了コードを返すため、目視の余地がありません。

これは実際に必要でした。開発中、境界線のコントラストが **2.52:1**（WCAG 1.4.11 の 3:1 未満）
だった箇所を手作業で見つけています。手で見つけたということは、**次は見逃す**ということです。

3つ目は、外部サービスへ渡すファイルに生の発言や実URLが残っていないかを検査します。
実際にこれで、`briefing.md` の発言引用が `content.md` へ転記されていた箇所を11件検出しました。
**渡さないと決めたファイルの中身が、渡すファイルへ移動していました。**
遮断はファイル単位では成立しません。

コントラストと禁止識別子の2つは `.claude/settings.json` の PostToolUse フックからも自動実行されます。
チェックリストは指示にすぎず、静かに飛ばされます。フックは飛ばされません。

> ただしフックが止めるのは**算術で決着がつくものだけ**です。
> 「要件と設計が矛盾していないか」のような判断は、人間のサインオフに残しています。

## 設計原則

- **文脈が設計を決める。嗜好ではない** ―― 根拠なき具体値は、それ自体が欠陥
- **要件は「何を」、設計は「どう」** ―― 解法を要件に書いた時点でトレードオフ検討は消える
- **凡庸さは中立ではなく失敗** ―― 既定の書体・グラデーション・角丸は「選択の放棄」
- **セキュリティは規約であり努力目標ではない** ―― `innerHTML` は設計段階で経路を断つ
- **PASS を出さない勇気** ―― 品質ゲートの価値は、通さなかった回数で決まる
- **検証は自己申告にしない** ―― 機械が判定できるものは、機械に判定させる

## 実例

> ⚠️ **以下は記入例です。** `/draft` 実行後、実際の結果に差し替えてください。

同じエージェントに、正反対の利用文脈を与えた結果です。

| 案件 | 利用文脈（C-3 / C-4） | D-01 輝度極性 | D-02 操作アンカー |
|---|---|---|---|
| 夜間の記録アプリ | 片手がふさがる・親指のみ／消灯後の室内 | **Dark** | 下端固定 |
| 屋外の設備点検 | 手袋着用・両手／屋外の直射日光下 | **Light** | 上端固定・大型ターゲット |

配色もレイアウトも、**私が選んだものではありません。**
「夜は照明を落としている」という一言（C-4）から輝度極性が、
「片手がふさがっている」という一言（C-3）から操作アンカーが、それぞれ根拠つきで導出されています。

導出の過程は各案件の `design.md`（設計判断 D-01 / D-02）に、
決定モデルそのものは [`design-decision-models.md`](.claude/knowledge/design-agent/design-decision-models.md) にあります。
