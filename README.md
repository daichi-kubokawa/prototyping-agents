# 仕様駆動プロトタイピング基盤

お客様と話しながら、その**対話の最中に**仕様を立ち上げ、そのまま画面まで到達させるための仕組みです。
ヒアリングの内容を入力すると、利用文脈の抽出から設計判断、Figma Make 用プロンプトの生成までが一続きに走ります。

仕様駆動開発（Spec-Driven Development）の実装のひとつですが、**仕様を作る場所が違います。**
机の上ではなく、お客様の目の前で作ります。

プロダクトには依存しません。深夜の暗室で片手操作されるアプリにも、真昼の屋外で手袋越しに触るアプリにも、
**同じエージェントがそれぞれ異なる正解を導出します。**

---

## なぜ作ったか

<!-- ★下書きです。ご自身の言葉に置き換えてください -->

はじめは、プロンプトを書きためていました。ヒアリングの内容を渡せば要件定義が出てくるものを、案件ごとに一枚ずつ。

うまくいかなかったのは、**プロンプトの中に答えが埋まってしまう**ことでした。
「背景はダークテーマ」「入力欄は画面下部」―― ある案件で正解だったものが、そのまま次の案件へ持ち込まれる。
屋外で使うアプリにも、夜の寝室向けの配色が出てくる。プロンプトが特定のプロダクトに癒着していました。

そこで答えを消し、**導出の手順だけを残しました。**
「暗いからダークテーマ」ではなく「環境照度と暗順応の状態から、背景輝度とコントラストを逆算する」。
同じエージェントが、正反対の利用文脈から正反対の答えを出せるようになりました。

もうひとつ作り直したのが、**検証の置き場所**です。
最初は各工程にレビューを挟み、通らなければ次へ進めない設計にしていました。
しかし商談中にそれは回りません。レビューする人間は自分自身で、そのとき自分はお客様と喋っているからです。

速さと堅さは相反するように見えて、**時間軸をずらせば両立しました。**
商談中は止まらない。検証は商談が終わってから、自分の机で回す。

速さは瞬発力ではなく、準備の構造で決まる ―― というのが、作ってみて得た結論です。

## 二層構造

再利用する仕組みと、案件ごとの成果物を分離しています。

```
再利用層  .claude/agents/     3体のエージェント定義
          .claude/knowledge/  方法論（決定モデル・規約・テンプレート）
          .claude/commands/   スラッシュコマンド
          prompts/            ワークフロー定義

案件層    examples/<案件名>/   ★実行時にゼロから生成される
```

**再利用層には、具体的な色値もフォント名もレイアウトも書かれていません。** これは欠落ではなく設計です。
すべての具体値は、`requirements.md` の利用文脈を決定モデルに代入した**計算結果**として導出されます。

案件層は、ヒアリングを始めるまで存在しません。対話の産物でない記述を先に置くと、
それは「導出」ではなく「コピー」になるためです。

## 二周構造 ―― DRAFT と DEVELOP

同じ成果物を2周します。**1周目は速く、2周目は堅く。**

| | **DRAFT** | **DEVELOP** |
|---|---|---|
| いつ | 商談中（お客様の目の前） | 商談後（自分の机） |
| 最適化するもの | 画面に到達するまでの時間 | 論理的無矛盾とトレーサビリティ |
| 検証ゲート | advisory ―― 記録するが止まらない | blocking ―― FAIL なら差し戻し |
| 目標 | 8分で画面へ | 制限なし |

検証ゲートでサインオフする人間は自分自身で、お客様の前では喋っています。
レビューは物理的に不可能であり、そこで止まるのはお客様の時間を捨てているだけです。
**ゲートは商談中ではなく、商談と商談の「あいだ」で回すもの**という設計です。

## 使い方

```bash
/preflight   # 商談前の点検（MCP疎通・設定・権限）
/draft       # 商談中。止まらずに画面まで走る
/develop     # 商談後。検証ゲートを通す
```

ヒアリング内容は3経路で渡せます。

```bash
/draft                              # FigJam から（MCP経由）
/draft 夜勤の看護師が、片手で…        # 直接入力
/draft @inputs/hearing.md           # 外部整理ツールの出力から
```

## 3体のエージェント

| エージェント | 役割 | 成果物 |
|---|---|---|
| `product-agent` | プロダクトマネージャー | `requirements.md`（利用文脈 C-1〜C-5、スコープ） |
| `design-agent` | テクニカルリード兼 UX デザイナー | `design.md`（ADR）/ `Guidelines.md` / `figma_make_prompt.md` |
| `quality-agent` | QA リード兼テクニカルライター | `review_history.md` / `tasks.md` / `README.md` |

3体は決まった記号で受け渡しをします。**この鎖が切れると設計が導出できません。**

```
product-agent        design-agent           quality-agent
C-1〜C-5        →    D-01 輝度極性     →    トレーサビリティ検査
（利用文脈）           D-02 操作アンカー        「D-01/D-02 は C のどれに由来？」
                                              遡れなければ差し戻し
```

たとえば「夜は電気をつけられない」という一言（C-4）から、
ダークテーマの採用（D-01）が**根拠つきで導出**されます。好みで選んではいません。

AWS Labs の [AI-DLC Workflows 2.0](https://github.com/awslabs/aidlc-workflows) のステージ体系とメタデータ仕様に準拠しつつ、
11体構成を3体へ集約しています。どの責務をどこへ吸収したかは、各エージェント定義の冒頭に明記しています。

## 設計原則

- **文脈が設計を決める。嗜好ではない** ―― 根拠なき具体値は、それ自体が欠陥
- **要件は「何を」、設計は「どう」** ―― 解法を要件に書いた時点でトレードオフ検討は消える
- **凡庸さは中立ではなく失敗** ―― 既定の書体・グラデーション・角丸は「選択の放棄」
- **セキュリティは規約であり努力目標ではない** ―― `innerHTML` は設計段階で経路を断つ
- **PASS を出さない勇気** ―― 品質ゲートの価値は、通さなかった回数で決まる

## 実例

> ⚠️ **以下は記入例です。** `/draft` 実行後、実際の結果に差し替えてください。

同じエージェントに、正反対の利用文脈を与えた結果です。

| 案件 | 利用文脈（C-3 / C-4） | D-01 輝度極性 | D-02 操作アンカー |
|---|---|---|---|
| 夜間の記録アプリ | 片手がふさがる・親指のみ／消灯後の室内 | **Dark** | 下端固定 |
| 屋外の設備点検 | 手袋着用・両手／屋外の直射日光下 | **Light** | 上端固定・大型ターゲット |

配色もレイアウトも、**私が選んだものではありません。**
「夜は照明を落としている」という一言（C-4）から輝度極性が、
「片手がふさがっている」という一言（C-3）から操作アンカーが、それぞれ根拠つきで導出されています。

導出の過程は各案件の `design.md`（設計判断 D-01 / D-02）に、
決定モデルそのものは [`design-decision-models.md`](.claude/knowledge/design-agent/design-decision-models.md) にあります。
