# README — night-app（夜間当直インフラ運用ダッシュボード）

> 本書は `design.md` に記録された ADR（設計判断）を要約したものであり、**新たな結論を持ち込まない**。
> 「なぜその構成を選んだのか」「何を棄却したのか」の一次情報は常に `design.md` にある。
> 本書と `design.md` の記述が食い違う場合は `design.md` を正とする（`CLAUDE.md` §5 整合性の優先順位）。

## 1. プロジェクト概要

夜間当直のインフラ運用L2担当者（`briefing.md` M-1〜M-23）が、単独運用の16時間シフト（17時〜翌9時）で、
監視アラート初動確認・サーバー再起動対応・深夜バッチ確認・緊急電話対応・朝の引き継ぎ準備という5工程を
並行/割り込みで処理しながら、判断根拠つきの対応記録を残すための業務プロトタイプ。

現状の課題は、深夜3時台の眠気による操作精度低下と誤入力リスク（M-12）、単独で下した判断を翌日
問われたときに自分を守れる記録が残っていないこと（M-22）、口頭のみの引き継ぎで情報が漏れること（M-3）に
集約される。本プロトタイプは、これらを **S01 当直ボード**（5工程の状態を一目で把握する）・
**S02 対応記録**（判断根拠つきで最小操作により記録する）・**S03 引き継ぎサマリ**（未完了事項を漏れなく
申し送る）の3画面で解く（design.md D-03）。

対象範囲は「確定した仕様と動くプロトタイプまで」であり、本実装（バックエンド連携・認証基盤・永続化）は
含まない（`CLAUDE.md` §3）。実装可能な単位への分解は `tasks.md` を参照。

## 2. アーキテクチャ意思決定の要約（design.md の ADR より）

### D-01: 輝度極性 ―― Dark（暗色基調・支配的な判断）
requirements.md C-4「22時に照明が自動減光（M-14）」「減光した室内と明るい画面の明暗差が目の疲労要因（M-18）」
が16時間中11時間（22時〜9時）にわたって低照度帯域に該当し、決定モデル①で Dark が強く優位となった。
Light基調は22時以降の明暗差を悪化させるため棄却。時間帯連動の両極性切替も検討したが、17〜21時側の
照度問題は requirements.md に明記されておらず、要求されていない機能を作らない（YAGNI）ため見送った。
17〜21時帯の視認性不満が次回商談で指摘された場合、またはオンコール対象化（OQ-2）で日中利用が加わった
場合に再検討する（design.md D-01）。

### D-02: 操作アンカー位置 ―― 画面下端固定・ターゲット幅拡大（支配的な判断）
requirements.md C-3「デュアルモニター常用」「仮眠室ではラップトップ（画面小）」「深夜3時台は立位操作・
手の重さでタイプミスが増える（M-12）」から、Fitts法則の評価に基づき、主要導線を画面下端に固定し
誤操作コストを吸収するW拡大を行った。サイドパネル固定はデュアルモニター利用時にモニター境界を跨ぐ
移動が増えるため棄却。中央フローティングは常時監視表示（M-10）を隠すため棄却した。オンコール対象化
（OQ-2）でスマートフォン単独操作が主になった場合、親指到達域基準の片手操作モデルへ再設計する
（design.md D-02）。

### D-03: 情報設計・画面構成 ―― 3画面構成（S01 当直ボード／S02 対応記録／S03 引き継ぎサマリ、支配的な判断）
requirements.md C-2「5工程が並行/割り込みで発生する」と、目的が異なる3系統――「状態を一目で把握する
（M-5〜M-10）」「判断根拠つきで記録する（M-12, M-22）」「翌当直者へ漏れなく申し送る（M-19の帰結）」――
から3画面を導出し、S01を戻り先とするハブ&スポーク型の遷移とした。5工程を個別画面に分ける案は工程間の
一覧比較ができなくなるため棄却。対応記録をS01内のインラインフォームにする案は複数行入力と確定前検証が
一覧性を圧迫するため棄却し、S02として分離した。引き継ぎサマリをS01の常設セクションにする案は当直中に
不要な情報を常時表示することになるため棄却し、S03として独立させた。Should Have「経験の浅い担当者への
手がかり提示」（M-2）が採用範囲に入った場合、または OQ-7（要承認フラグの割当）が確定した場合、画面構成
・条件付き表示ロジックの見直しを要する（design.md D-03）。

### D-04: 技術構成 ―― クライアントサイド完結・追記専用（Append-only）の記録構造（推奨構成）
requirements.md §5.1「一度確定した記録は事後に上書き・削除されず、追記としてのみ反映される」、
§5.2「メール／チャットの2経路のうち一方が利用できなくても業務が完全に止まらない」から導出した。
プロトタイプ段階で簡易バックエンド（モックAPI）を構築する案は、商談用プロトタイプの目的に対して
過剰投資でありYAGNIに反するため棄却。記録を可変（UPDATE可能）なレコードとして設計する案は§5.1の
改ざん耐性要件に直接抵触するため棄却した。**本決定は「引き渡し時の推奨構成」であり、実装フェーズを
拘束しない**（本実装への引き渡し時は、記録ストアを追記専用スキーマとすること、アラート取り込みを
メール／チャットで独立ハンドリングすることを推奨構成として明記している）。記録の保持期間・閲覧権限
範囲（Assumptions記載の未確定事項）が確定した場合、ストレージ選定とアクセス制御の設計を追加で行う
必要がある（design.md D-04）。

## 3. セキュリティ設計境界（design.md §6 より）

- **改ざん耐性・追記性**: 確定後の `Record` は不変（Immutable）とする。update／delete のAPI自体を
  実装せず、UIにも「編集」ボタンを設けない。訂正が必要な場合は「追記する」導線のみを提供する
  （requirements.md §5.1、design.md §6.2）。タイムスタンプ（`recordedAt`）はクライアント入力を許可せず、
  システム時刻から自動採番する
- **秘匿情報の保持境界**: requirements.md §5.1／Assumptionsは「記録の保持期間、および担当者本人以外の
  誰が閲覧できるかという範囲」を本イテレーションでは扱わないと明記している。design.md はこの境界を
  先回りして確定させず、プロトタイプ段階でローカルストレージ等への永続化やアクセス制御を独自に追加
  していない（要件に無い機能を作らない、design.md §6.3）
- **DOM バインド規約**: `innerHTML` / `outerHTML` / `insertAdjacentHTML` / `document.write` の全面禁止、
  `textContent`/`createElement`/`addEventListener` の使用義務、禁止識別子リストは `Guidelines.md` §8・
  `figma_make_prompt.md`「実装コードを生成する場合」節に転記済み（`.claude/knowledge/shared/frontend-security.md`
  準拠）。判断根拠入力欄（S02）と対応記録一覧（S01「最近の対応記録」・S03「対応記録一覧」）が、担当者の
  自由記述テキストを再表示する最も攻撃面の広い箇所であり、すべての再表示経路で `textContent` 経由の
  バインドを徹底する（design.md §6.1）
- **要承認フラグによるアクセス抑止**: `requiresApproval: true` の工程（M-20: ストレージ／ネットワーク
  変更等）は、完了への遷移導線自体をUIに提示しない設計とする。到達できない操作を、誤操作しうる形で
  存在させないという設計思想（design.md §5、D-02の逆用）
- **認証・認可の扱い**: 実装自体は本フレームワークの範囲外（D-04）。`tasks.md` の各 Bolt の DoD は、
  UI設計として想定外の遷移導線が無いことの確認までを検証範囲とする

## 4. 次回確認事項（申し送り）

- **OQ-1・OQ-2 は C-1/C-3/C-4 の確定に関わるため優先確認とする**（requirements.md 末尾の指定）。
  OQ-1（視力/色覚特性未確認）はD-01のコントラスト到達目標に、OQ-2（オンコール担当者を対象に含めるか）
  はD-02の操作アンカーに、それぞれ影響しうる
- **OQ-7**: 対応工程の「要承認フラグ」が、現状の画面実装では5工程中「再起動対応」にのみ true として
  割り当てられている。一方 requirements.md M-20 は「再起動程度の対応は自分の判断で実行できる」
  「ストレージ構成変更・ネットワーク経路変更など踏み込んだ作業が要承認」と述べており、再起動対応自体を
  要承認とする記述ではない。この割り当てが承認要否の分岐を示すための代表例（仮の実装）なのか、実際の
  運用と異なる割り当てなのか、次回商談で確認が必要（requirements.md §4、design.md §10）
- **OQ-4**: 対応ログの現在の記録先・フォーマットが不明。既存システムとの統合方式は D-04 の推奨構成に
  影響する
- **OQ-8・OQ-9**: タイムスタンプの固定ラベル文字列の要否、「シフト残り時間」表示を正式なShould Have
  として位置づけるかどうかは、いずれも設計への実質的な影響は無いが、次回商談での確認事項として残る
- **顧客反復ログ（review_history.md）**: 「もう少し背景を明るく」という要望（`--bg`）が実際に適用された
  結果かどうか、適用前の値の記録が無いため機械的には確認できていない（OQ-6）。次回商談で現状の暗さで
  十分かを人間に確認することを推奨する
- **OQ-10**（IT-2 開放的レビュー由来）: S02 判断根拠入力中の割り込み（特に M-8 緊急電話対応）に対する
  下書き保持機構が現状無い。Should Have 相当の要件として追加するか、次回商談で確認する
- **OQ-11**（IT-2 開放的レビュー由来）: メイン当直者からオンコール担当者（M-1）への連絡・エスカレーション
  導線が、既存の聞き取り内容に言及がない。今回のスコープに含めるか、次回商談で確認する
- 検証履歴・監査証跡の一次情報は `review_history.md`（追記専用）。開放的レビューで検出した追加検討事項
  （V-1〜V-4にもDRAFT保留指摘にも該当しない改善提案）は、`review_history.md` への反映可否をオーケストレータ
  が採否判断したうえで記録する
