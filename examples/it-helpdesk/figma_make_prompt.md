# figma_make_prompt.md — Figma Make 連携プロンプト（DRAFT）

> 形態B（ポインタ型）：`screens.md` / `content.md` が存在するため、内容を直接埋め込まず
> 「どのファイルを読むか」の指示書とする。以下をそのまま Figma Make に貼り付け、
> `screens.md` / `content.md` / `Guidelines.md` / `design.md` / `requirements.md` をアップロードすること。
> `briefing.md` は渡さない（生ヒアリング内容を含むため）。

---

## Task

社内 IT・情報システム担当チーム（3名）が、Slack・メール・口頭に分散した問い合わせを一元管理し、
対応の重複・放置・属人化を防ぐための、デスクトップ向け問い合わせ管理ツールのプロトタイプ画面を
以下3画面分生成してください。これは実装前の「動作する見た目」であり、本番実装ではありません。
バックエンド連携は不要ですが、**空状態と条件分岐は必ず含めてください**。

## Context

- ターゲットユーザー：社内 IT 担当者3名。専門知識を持つ熟練者だが、複数の問い合わせを並行処理しながら
  緊急の割り込みにも対応するため、業務時間中の認知的余力は低い状態にあると推測される
- 利用シーン：社内オフィスでの PC 着座業務が中心（推測）。マウスによる操作が主と推測される
- トーン：業務ツールとして情報の見通しの良さと即応性を優先する。装飾よりも階層と発見可能性を重視する
- 技術構成：単一 HTML／CSS／Vanilla JS を想定したプロトタイプ（フレームワーク不使用）

## 読むファイルと役割

| ファイル | 役割 |
|---|---|
| `screens.md` | 画面構成（S01〜S03）・遷移・表示要素・アクション・空状態と条件分岐 |
| `content.md` | 画面に表示する実際の文言（状態・緊急度のラベル語彙、空状態文言） |
| `Guidelines.md` | カラートークン・タイポグラフィ・スペーシング・コンポーネント寸法 |
| `design.md` | D-01（Light 採用）・D-02（行内インラインアンカー）の根拠 |
| `requirements.md` | Must Have の受入基準、非機能要件、Open Questions |

## 優先順位（迷ったときの判断）

1. **何を画面に出すか** → `screens.md` の「表示要素」と「アクション」が最優先
2. **その文言は何か** → `content.md` の記載をそのまま使う
3. **どう見せるか** → `Guidelines.md` のトークンのみを使う
4. **なぜそうなのか** → `design.md` の ADR。この2つの判断を覆さないこと
   - D-01 輝度極性: Light
   - D-02 操作アンカー: 一覧の各行内に常設したインラインアンカー（画面全体固定のフローティング
     ボタンは使わない）

記述が矛盾した場合は、上の番号が小さい方を優先してください。

## 絶対に守ること

### 文言
- 本文テキストは推測で生成せず、**必ず `content.md` の記載をそのまま使用**すること
- **ダミーテキスト・プレースホルダー・ロレムイプサムでの生成を禁止**します
- `content.md` に無い文言（依頼者向け進捗共有メッセージの本文など）が必要になった場合は、
  **生成せずにその旨を明示**してください

### 表示の分岐
- `screens.md` の「表示の分岐」に従い、**空状態**（問い合わせ0件・検索結果0件）と
  **条件付き表示**（対応者が確定している行、対応済みの詳細画面など）を必ず実装してください
- 正常系だけの画面は、動かした瞬間に破綻します

### 構成（階層・近接・整列）
- `screens.md` で `［第1］` が付いた要素を、その画面で**最も強い一要素**として扱ってください。
  強調は**ウェイト・サイズ・字間**で作り、色や影で作らないこと
- `screens.md` の「段階的開示」に挙がった要素（対応済みの行、依頼者の詳細連絡先）は、
  **初期表示に出さない**でください
- 要素の群は、群の外側の余白（`24px`）を内側（`8px`）の2倍以上取って分けてください
- 垂直の軸を1〜2本に絞り、テキスト左端とアイコン中心を揃えてください。
  間隔にはリズムを付けてよいが、軸は崩さないこと

### 意匠（禁則事項 P-1〜P-6）
- **P-1** 意味を持たない装飾グラデーション背景・根拠なきグロー・既定値のグラスモーフィズムを使わない
- **P-2** Inter / Arial / Helvetica（既定値としての）/ Roboto / system-ui を無思考に採用しない。
  `Guidelines.md` が指定する `IBM Plex Sans` / `Noto Sans JP` を実体名で使う
- **P-3** 角丸・影・境界線を全要素に一括適用しない
- **P-4** 絵文字によるアイコン代替、多色イラストの安易な配置をしない
- **P-5** 意味なく中央揃えされた長文、全要素の等間隔配置を避ける
- **P-6** 彩度の高い色を広面積で使わない。`--color-accent` / `--color-urgent` は面積比数％以内の
  「点」用途（ボタン・バッジ）に限定する（緊急度は色に加えて必ずラベル文字を併記すること）

### 実装コードを生成する場合（DOM バインド規約・例外なき禁止）
- `innerHTML` / `outerHTML` / `insertAdjacentHTML` / `document.write` による
  ユーザー入力・外部応答・AI 生成テキストの展開を**全面禁止**
- 動的要素は `document.createElement()` で生成し、テキストは `.textContent` 経由でのみバインドする
- URL を解釈する属性（`href` / `src` / `formaction`）は `setAttribute()` で設定し、
  `javascript:` / `data:` スキームを拒否する
- イベントは `addEventListener` のみ。インライン `onclick=`、`eval()`、`new Function()`、
  文字列引数の `setTimeout` を禁止する
- テンプレートリテラルによる HTML 文字列組み立てを禁止する
- フレームワークのエスケープ回避 API（`dangerouslySetInnerHTML`、`v-html` 等）も禁止する

**禁止識別子（grep で検知する）**
```
innerHTML
outerHTML
insertAdjacentHTML
document.write
eval(
new Function(
dangerouslySetInnerHTML
v-html
```

### 秘匿情報
- 実URL・アクセスキー・個人が特定される情報を出力に含めないこと。
  依頼者の氏名・端末情報のサンプルは、実在を想起させない一般的な表記に留めること

## 本プロトタイプの位置づけ

> 表示コンテンツ（状態・緊急度のラベル語彙を含む）は要件から導出した**仮説**であり、
> 実務上の妥当性は未検証です。次回商談での確認対象であり、確定デザインとして扱わないでください。
