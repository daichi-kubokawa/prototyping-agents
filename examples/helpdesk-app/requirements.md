# requirements.md — 要件定義書

## 1. ペルソナと利用文脈（Context of Use）

### C-1 ユーザー
社内IT・情報システム担当チーム3名（M-1）。ITの専門知識を持つ社内スタッフで、複数の問い合わせを並行して処理しながら（M-20）、緊急対応が通常業務に割り込む状況下で判断を行う（M-21）ため、認知的余力は常に逼迫している。年齢層・視力/色覚特性は既存の聞き取り内容に記載がなく、OQ-1 に準じ未確定（一般的な就労者を仮定）。

### C-2 タスク
1セッションの操作は、問い合わせの状況確認・記録・他担当者への引き継ぎ（M-23）が中心。連続注視時間は業務時間中の並行処理により細切れになりやすい（M-20）。記録漏れ・重複対応（M-4, M-5）は即座の業務手戻りを生むが、致命的な不可逆性を示す記述はない。

### C-3 装置と入力方式
既存の聞き取り内容に明示的な記述なし（OQ-1）。オフィス内での常駐対応という M-1 の性質から、デスクトップ／ノートPC・キーボード・マウス操作を仮定するが未確認。

### C-4 物理環境
既存の聞き取り内容に明示的な記述なし（OQ-2）。通常のオフィス照度・業務時間内での利用を仮定するが、緊急対応が時間外に及ぶか（M-21）は未確認。

### C-5 社会的・組織的環境
社員名・端末情報などの個人情報を安全に扱う必要がある（M-18）。3名の少人数チームで無理なく運用できることが前提（M-16）。既存のSlack運用を活かす方針が示されている（M-15）。

> 本節は design-agent の D-01 / D-02 の入力である。C-3 / C-4 は推測で埋めた項目のため、§6 Assumptions に転記する。

## 2. 認知的・身体的ペイン
- 問い合わせ窓口がSlack・メール・口頭に分散し、確認漏れと重複対応が起きやすい（M-3, M-4, M-5）
- 対応状況・優先順位が担当者個人の記憶に依存し、担当交代や休業時に引き継げない（M-6, M-8, M-23）
- 過去事例の参照に時間がかかり、緊急対応が割り込む中での判断負荷が高い（M-7, M-12, M-21）

## 3. MoSCoW 優先順位マトリクス

### Must Have（本イテレーションで必須）
- 全ての問い合わせを一箇所で可視化できること（M-9）。検証: 複数チャネル由来の問い合わせが単一の一覧で確認できる
- 対応者と対応状況が全員に明確であること（M-10, M-11）。検証: 誰がどの問い合わせに対応中かを他メンバーが即座に判別できる
- 緊急度の高い問い合わせを即座に見分けられること（M-12）。検証: 一覧上で緊急度による識別が可能
- 過去の対応履歴を素早く検索・参照できること（M-7, M-13）。検証: 類似の過去問い合わせに一定時間内で到達できる
- 依頼者へ進捗を伝えやすいこと（M-14）。検証: 依頼者が対応状況を都度問い合わせずに把握できる手段が存在する。**ただし** その手段が担当者側からの受動的な共有（画面提示・手動連絡等）で足りるのか、システムからの能動的な通知（状態変化時の自動送信等）を必須とするのかは既存の聞き取り内容に明記が無く断定できない（OQ-5 参照）。OQ-5 解消までは受動的な共有で暫定的に充足するものとする
- 3名の少人数でも複雑な操作を増やさず運用できること（M-16, M-17, M-19）。検証: 導入前の運用手順数から増加しない
- 既存のSlack運用を活かせること（M-15）。検証: 少なくとも問い合わせのチャネル種別としてSlack由来の情報が識別できる（受動表示）。Slack上での通知やBot操作等、システムとSlackが双方向で連携する能動的な機能まで必須とするかは断定できない（OQ-5 参照）。OQ-5 解消までは受動表示で暫定的に充足するものとする
- 社員名・端末情報等の個人情報を安全に扱えること（M-18）。検証: アクセス可能範囲が担当チームに限定される

### Should Have / Could Have

**Should Have**
- 優先順位判断の根拠を個人の記憶に頼らず可視化・共有できること（M-6）。検証: 緊急度等の判断基準に基づき一覧を並び替え・整列できる
- 担当者交代時の引き継ぎ内容を記録・参照できること（M-23）。検証: 対応途中で担当者が変わった際、前任者の対応履歴・申し送り事項を後任者が参照できる
- 対応ノウハウ・解決方法を構造化して蓄積し、属人化を緩和できること（M-8）。検証: 対応方法を知る担当者が不在でも、記録された対応履歴から解決手順に到達できる（M-13 の履歴検索を補強する）

**Could Have**
- 複数の問い合わせを並行して処理する際、作業状態を一時保存し中断・再開できること（M-20）。検証: 対応を中断した問い合わせへ後から素早く復帰できる
- 担当者間での状態変化をより即時に把握できる仕組み（M-22）。検証: ある担当者の更新が他の担当者の画面へ遅滞なく反映される

### Won't Have（今回は対象外）
- 承認ワークフローやSLA自動計算等、大規模ITSM/ITILスイート相当の機能（M-19「重いツールを導入したくない」より対象外）
- Slackからの完全移行・Slack運用の廃止（M-15より、既存チャネルを活かす方針のため対象外）
- 依頼者側の新規問い合わせチャネル（電話窓口等）の構築（要求に言及なし）

## 4. 中核データ構造

中心エンティティは「問い合わせ」1種であり、`screens.md` の S01（一覧）・S02（詳細）はいずれもこのエンティティの異なる表示形態である。以下は永続化方式ではなく、論理属性と不変条件の規定にとどめる。

### 4.1 「問い合わせ」の属性

| 属性 | 由来（M-番号） | 備考 |
|---|---|---|
| 件名 | M-9（一覧で識別するために必要） | 問い合わせ内容を一意に識別する短い表現 |
| 依頼者 | M-14, M-18 | 進捗共有・個人情報保護の両方の対象になる人物情報 |
| チャネル（Slack／メール／口頭） | M-2, M-3, M-9, M-15 | 分散した窓口を一箇所に集約するために、由来を記録する属性。値の集合は M-2 に列挙された3種に限る |
| 緊急度 | M-6, M-12 | 一覧上での識別対象。要件文書内では「緊急度」を一次語とする（`screens.md` 等の「優先度」表記との統一は design-agent 側の検証ゲート課題として別途指摘済み） |
| 対応状況 | M-10, M-11 | 「対応者・状況が全員に明確であること」を満たすための状態属性 |
| 担当者 | M-10, M-4, M-5 | 重複対応・放置（M-4, M-5）を防ぐため、対応中の問い合わせに対する担当者の一意性が求められる |
| 受信日時 | M-2, M-9 | 一覧化・並び替えの基準となる時刻情報 |
| 対応履歴 | M-7, M-8, M-13 | 過去の対応内容を素早く参照するための記録。時系列に追記される |

### 4.2 不変条件（Invariant）

- **担当の一意性**: ある時点で「対応中」の問い合わせに、同時に複数の担当者が割り当てられた状態を許容しない（M-5「複数人が同時に返信しそうになる」を防ぐ制約）
- **履歴の追記性**: 対応履歴は過去の記録を上書きせず、追記によってのみ増える（M-7, M-13「過去の対応内容を参照したい」を満たすには、記録が消えないことが前提になる）
- **チャネルは単一値**: 1件の問い合わせが持つチャネルは1つに定まる（M-2 の記述に基づく。複数チャネルにまたがる問い合わせをどう1件に集約するかは、既存の聞き取り内容に記述が無く未確定）

### 4.3 未確定の属性値（OQ-6 と関連）

担当者が**未確定のまま登録される状態**（新規受付直後、口頭受付分など）を許容するかどうかは既存の聞き取り内容に記述が無い。許容する場合、担当の一意性（4.2）は「未確定 → 特定の1名」への遷移として扱う必要があるが、この遷移の起点となる状態自体が要件として定義されていない。詳細は §6 Open Questions の OQ-6 を参照。

## 5. 非機能要件

### 5.1 セキュリティ
- 社員名・端末情報等の個人情報は、対応チーム3名（M-1）の範囲でのみ閲覧可能でなければならず、それ以外の経路（チーム外への共有・エクスポート等）から到達可能であってはならない（M-18）
- 保持期間・アクセス権限の粒度・社外持ち出し規定など、ライフサイクルの具体的な境界は既存の聞き取り内容に明記が無く未確定（OQ-4 を参照。確定するまでは「必要最小限の範囲・期間に限定する」という原則のみを既定とする）
- 漏洩時の影響範囲は、社内300名規模の組織における特定個人の識別（氏名・使用端末の紐付け）であり、対応チーム外の第三者にとって当該情報が有用にならないよう扱うこと

### 5.2 耐障害性
- Slack連携（M-15）が利用できない状態であっても、問い合わせの一覧化・対応状況の記録・履歴参照という中核機能（M-9〜M-13）は継続して利用できること。Slack連携を、中核機能が依存する単一障害点にしてはならない
- 3名の少人数運用（M-16）を前提とするため、外部依存の障害時に復旧手順そのものが専任の対応要員を必要とする設計は避けること（M-17「複雑な操作や手順を増やさない」に反する）

### 5.3 アクセシビリティ
- C-1 に明示的な視力・色覚特性の記述は無く（既存の聞き取り内容に言及なし）、一般的な社内就労者を仮定する前提の上に立つ（§6 Assumptions 参照）。この前提が崩れる情報が確認された場合、到達目標を再設定する必要がある
- 緊急度・対応状況等の識別（M-12, M-10）を色のみに依存させないこと。C-1 で仮定した「一般的な就労者」には色覚特性の多様性が含まれ得るため、色以外の手段（文字・形状等）を併用する制約とする

## 6. Assumptions（前提・推測）と Open Questions（要確認事項）

### Assumptions
- C-3（装置）: デスクトップ／ノートPC・キーボード・マウス操作を仮定（明示的記述なし）
- C-4（物理環境）: 通常のオフィス照度・業務時間内利用を仮定（明示的記述なし）
- 担当チーム3名は社内情報システム部門に常駐すると仮定（M-1 より推測）

### Open Questions
- OQ-1: 担当者のデバイス種別・画面サイズ・入力方式（C-3）が未確認
- OQ-2: 対応時の物理環境（C-4：照度・時間帯・夜間対応の有無）が未確認
- OQ-3: 依頼者側（問い合わせ元社員）の利用文脈・代替端末の有無
- OQ-4: 個人情報の安全な取り扱いの具体範囲（保持期間・アクセス権限粒度等）
- OQ-5: 「Slackを活かした運用」がSlack連携を指すか、Slack移行回避の制約を指すかの確認。あわせて、M-14「進捗を伝えやすくしたい」・M-15「Slackを活かした運用」の両方について、**受動的な表示（チャネルタグ等）で足りるのか、能動的な通知・共有機能（状態変化時の自動通知、Slack Bot連携等）を必須とするのか**を次回商談で確定する必要がある（§3 Must Have 該当箇所を参照）
- OQ-6: 新規受付時・口頭受付分など、担当者が未確定のまま登録される問い合わせを許容するか。許容する場合、一覧・詳細でどう表示し、誰が拾う想定か（M-9〜M-11 関連）。`figma_output/01_2026-08-11` の実プロトタイプでは「未割り当て」という状態値が独自に補われていたが、これは既存の聞き取り内容にも本書にも定義が無く、design-agent が実装上の必要から補ったものである（§4.3 参照）
