# README — helpdesk-app（社内IT問い合わせ管理プロトタイプ）

> 本書は `design.md` に記録された ADR（設計判断）を要約したものであり、**新たな結論を持ち込まない**。
> 「なぜその構成を選んだのか」「何を棄却したのか」の一次情報は常に `design.md` にある。
> 本書と `design.md` の記述が食い違う場合は `design.md` を正とする（`CLAUDE.md` §5 整合性の優先順位）。

## 1. プロジェクト概要

社内IT・情報システム担当チーム（3名）が、Slack・メール・口頭に分散した問い合わせを並行処理しながら、
状況確認・記録・他担当者への引き継ぎを行うための業務プロトタイプ（`briefing.md` M-1〜M-24）。

現状の課題は、窓口の分散による確認漏れ・重複対応（M-3〜M-5）、優先順位判断の属人化（M-6）、
過去事例参照の遅さ（M-7〜M-8）に集約される。本プロトタイプは、これらを**S01 問い合わせ一覧**
（全体を俯瞰して緊急度・対応状況を即座に把握する）と**S02 問い合わせ詳細**（1件に集中して記録・引き継ぐ）
の2画面で解く（design.md D-03）。

対象範囲は「確定した仕様と動くプロトタイプまで」であり、本実装（認証・永続化・バックエンド連携）は含まない
（`CLAUDE.md` §3）。実装可能な単位への分解は `tasks.md` を参照。

## 2. アーキテクチャ意思決定の要約（design.md の ADR より）

### D-01: 輝度極性 ―― Light（非支配的な判断）
物理環境（C-4）が `briefing.md` に明示記述が無く未確定（OQ-2）のため、決定モデル①の既定分岐として
Light を採用した。夜間・時間外の緊急対応（M-21）が常態化していると判明した場合、Dark 側への加点が
発生し得るため、OQ-2 が確定次第、再評価する（design.md D-01）。

### D-02: 操作アンカー位置 ―― デスクトップ標準配置（非支配的な判断）
装置・入力方式（C-3）が同じく未確定（OQ-1）のため、PC・マウス操作を仮定する既定分岐として、
グローバル操作を上部固定、主要導線を各画面右上に置く構成を採用した。タブレット・タッチ操作等が
判明した場合、到達可能領域の再モデリングが必要になる（design.md D-02）。

### D-03: 情報設計・画面構成 ―― 2画面構成（S01 一覧／S02 詳細）
requirements.md C-2「俯瞰して探す」（一覧を見る認知モード）と「1件に集中して記録・引き継ぐ」
（詳細を見る認知モード）という2つの異なる目的から、Must Have を束ねて画面を導出した。
単一画面への統合案は、認知的余力が逼迫した状態（C-1）で2つの情報密度が同時に視界に入り
段階的開示が機能しなくなるため棄却。3画面以上への分割案は、3名の少人数運用で操作を増やさない
という制約（M-16/M-17/M-19）に反するため棄却した（design.md D-03）。

### D-04: 技術構成 ―― バックエンド連携を前提としないクライアント側完結の軽量構成（推奨）
Won't Have「大規模 ITSM/ITIL 相当の機能は対象外」（M-19）と、耐障害性要件「外部依存の障害時に
専任要員を要する設計を避ける」（§5.2）から導出した。大規模プラットフォーム採用、および
Could Have の M-22（リアルタイム反映）を前提とした常時同期基盤は、いずれも現イテレーションの
Must Have を超えるため YAGNI により棄却した。**本決定は「引き渡し時の推奨構成」であり、実装フェーズを
拘束しない**（design.md D-04、`artifact-templates.md` の規定どおり）。

## 3. セキュリティ設計境界（design.md §6 より）

- **保持境界**: 社員名・端末情報等の個人情報は、対応チーム3名の範囲でのみ閲覧可能とし、
  それ以外の経路（チーム外への共有・エクスポート等）から到達可能な導線を設計に含めない（M-18、requirements.md §5.1）
- **保持期間**: OQ-4（保持期間・アクセス権限粒度）が未確定のため、「必要最小限の範囲・期間に限定する」
  という原則のみを既定とし、確定的な自動削除・アーカイブ機能は OQ-4 解消まで設計しない
- **権限粒度**: 要件にはチーム3名という単位でのアクセス制御のみが記述されており、チーム内でのロール分割
  （閲覧専用／編集可能等）は要件に無いため、フラットな権限モデルを前提とし、それ以上の分割機能は持ち込まない
- **DOM バインド規約**: `innerHTML` / `outerHTML` / `insertAdjacentHTML` / `document.write` の全面禁止、
  `textContent`/`createElement`/`addEventListener` の使用義務、禁止識別子リストは `Guidelines.md` §8・
  `figma_make_prompt.md` Constraints 節に転記済み（`.claude/knowledge/shared/frontend-security.md` 準拠）
- **認証・認可の扱い**: 実装自体は本フレームワークの範囲外（D-04）。`tasks.md` の各 Bolt の DoD は、
  UI 設計として送出導線が無いことの確認までを検証範囲とする
