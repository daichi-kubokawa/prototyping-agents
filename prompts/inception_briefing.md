# 1. 実行パラメータ

値は `local_env.json`（Git 追跡外）からバインドする。
**本ファイルに実データを書き込んではならない**（シークレットリーク防止）。

```
MODE              DRAFT | ITERATE          実行モード（§2）
PROJECT_NAME      文字列                   プロダクト名
OUTPUT_DIR        相対パス                 成果物の出力先ディレクトリ
PROJECT_SUMMARY   文字列                   一行概要
FIGJAM_URL        URL                     ヒアリング整理先（Figma MCP 経由で取得）
RAW_HEARING_MEMO  文字列 or ファイルパス      FigJam が使えないときの入力
```

- `MODE` はコマンド（`/draft` `/iterate`）が設定する。`local_env.json` には不要
- `RAW_HEARING_MEMO` は `$ARGUMENTS`（コマンドの引数）で上書きされる。**引数が優先**
- `OUTPUT_DIR` が未設定だと出力先が決まらず実行できない

### `OUTPUT_DIR` の決め方

本リポジトリは**雛形と実演を同居させる**ため、案件ごとにサブディレクトリを切る。
実案件では **1リポジトリ = 1案件**とし、リポジトリ直下に近い場所へ出力する。

```
examples/<案件名>    本リポジトリ（複数の実演を並べて比較するため）
spec                 実案件（Template から生成した専用リポジトリ）
```

# 2. 二周構造 ―― DRAFT パスと ITERATE パス

本フレームワークは、**同じ成果物を2周**する。1周目は速く、2周目は堅く。
これは「簡易版」と「完全版」ではなく、**最適化する対象が違う2つの周回**である。

| | **DRAFT** | **ITERATE** |
|---|---|---|
| **いつ** | 商談中（お客様の目の前） | 商談後（自分の机） |
| **最適化対象** | 画面に到達するまでの時間 | 論理的無矛盾とトレーサビリティ |
| **検証ゲート** | **advisory** ―― 記録するが停止しない | **blocking** ―― FAIL なら停止・差し戻し |
| **人間の停止** | **なし**（喋っているため物理的に不可能） | 各ゲート後にサインオフ待ち |
| **生成物** | `briefing` / `requirements`（最小）/ `design`（D-01・D-02のみ）/ `Guidelines` / `figma_make_prompt` | 上記の検証と補完。`detailed_spec` 等の追加 |
| **目標時間** | 画面到達まで8分以内 | 制限なし |

### 反復は2つある ―― 対象が違う

「反復」という語が2箇所に出てくるため、対象で区別すること。

| | **DR-3 顧客反復**（商談中） | **ITERATE 仕様反復**（商談後） |
|---|---|---|
| **回すもの** | **画面**（Figma Make の出力） | **仕様書**（requirements / design / …） |
| 道具 | Figma Make ＋ `/log`（記録のみ） | `/iterate` |
| 仕様書 | **触らない** | 更新する |

**商談中に仕様書を直しにいくと止まる。** だから画面だけを回し、
「何を直したか」を `/log` で3秒だけ残す。その伝票を商談後に `/iterate` が精算する。

```
/log もっと明るく → 背景トークン
        ↓  review_history.md「顧客反復ログ」
/iterate が読んで requirements.md / design.md へ反映
```

商談が終わった時点で**画面と仕様はズレている。** そのズレの解消が `/iterate` の第一の仕事である。

---

**この2周の外側に実装は無い。** 本フレームワークの範囲は、確定した仕様と動くプロトタイプまでである（§6 スコープ外）。

```
仕様パス（同じ成果物を2周）    /draft  →  /iterate
```

> **なぜ分けるのか**
> 検証ゲートでサインオフする人間は、あなた自身である。そしてお客様の前で、あなたは喋っている。
> レビューは物理的に不可能であり、そこで止まるのはお客様の時間を捨てているだけである。
> **ゲートは商談中に回すものではなく、商談と商談の「あいだ」で回すもの。**
> こうすることで、商談中は速く、商談後は堅く、次の商談は前回より精度が高い状態で始まる。

**DRAFT で作った成果物を、ITERATE で検証・補完する。捨てる作業は一切ない。**

# 3. 本フレームワークの位置づけ

人間が定義した最上流のインプット（PROJECT_SUMMARY / FIGJAM_URL / RAW_HEARING_MEMO）を SSoT とし、
`.claude/agents/` に定義された専門エージェントへコンテキストスイッチしながら仕様を展開する。

**本フレームワークはプロダクトに依存しない。** 深夜の暗室で使う記録アプリにも、屋外・日中の点検アプリにも、
同一のフローで適用できる。特定プロダクトの答え（配色・レイアウト・技術構成）を本プロンプトに書いてはならない。

| エージェント | 定義 | 担う成果物 |
|---|---|---|
| `product-agent` | AI Product Manager | `briefing.md` / `requirements.md` |
| `design-agent` | AI Technical Lead & UX Designer | `design.md` / `Guidelines.md` / `figma_make_prompt.md` |
| `quality-agent` | AI QA Lead & Technical Writer | `review_history.md` / `tasks.md` / `README.md` |

# 4. 最優先ガードレール（全モード共通）

**モードによって緩めてよいのは「停止するかどうか」だけである。以下は DRAFT でも一切緩まない。**

> **正は `.claude/knowledge/shared/guardrails.md` にある。** ここに再掲しているのは、
> オーケストレータが `guardrails.md` を読まないためである（あれはサブエージェントが
> Knowledge Loading で読む）。**両者が食い違った場合は `guardrails.md` を正とし、ここを直す。**

- **シークレット情報のマスク**：`local_env.json` 由来の生データ（実URL、アクセスキー、
  個人が特定される生ヒアリング内容）を平文出力しない。`[Confidential]` 等へ置換する。

- **生の発言を下流へ転記しない**：`briefing.md` を外部へ渡さない判断は、
  発言を引用の形で下流へ転記した時点で無効になる。**由来は識別子（`M-n` / `C-n`）で示す。**
  これを機械判定するのが S-5（DR-2b）である。

- **層の厳守（要件と解法の分離）**：上流に技術的解法を書かない。書くのは目的と制約である。
  「単一 HTML で実装する」ではなく「ビルド工程なしで配布でき、開くだけで起動できること」。

- **ゼロ・ハードコード**：再利用層に具体的な色値・書体名・レイアウトを書かない。
  具体値は利用文脈を決定モデルに代入した計算結果としてのみ出力する。

- **DOM バインド規約**：`innerHTML` 系の禁止と `textContent` / `createElement` 規約は
  DRAFT でも省略しない。**速度のために安全性を落とさない。**

- **推測・不足情報の可視化**：上流に無い情報を下流で確定事項として捏造しない。
  推測は **Assumptions**、不足は **Open Questions** として明示する。

- **識別子を記憶で書かない**：`C-n` `M-n` `D-n` `P-n` `S-n` `V-n` は別体系である。
  引用元を開いて実在を確かめること（`guardrails.md` §7）。

- **案件層はゼロから生成される（初回に限る）**：`{{OUTPUT_DIR}}/` は初回実行時に新規作成する。
  **ヒアリング前**にこの配下へ何かを置いてはならない。ただし2回目以降は前回の成果物を引き継ぐ。
  禁じているのは「**対話を経ていない記述を先に置くこと**」であって、前回の対話結果を捨てることではない。

- **整合性の優先順位**：`briefing.md` → `requirements.md` → `design.md` → `Guidelines.md`
  → `figma_make_prompt.md` → `tasks.md`

- **言語規約**：思考プロセスと出力するすべての Markdown は日本語で統一する。

# 6. 実行ステップ

## ■ DRAFT パス ―― 商談中（実測: 約12分で Figma Make 用プロンプトまで）

> このパスでは **一切停止しない。** 検証は advisory であり、指摘は `review_history.md` の
> `## 保留指摘（DRAFT）` へ溜めるだけにする。差し戻しも再生成も行わない。
> 判断はすべて ITERATE パスに繰り延べる。

### DR-1. 原点構築と要件定義（`product-agent` へ**1回だけ**委譲）

> **委譲回数を最小にする。** 同一エージェントが連続して作る成果物は、
> **1回の委譲の中で逐次生成させる。** 呼び出しごとにコールドスタートが乗り、
> 商談中はそれがそのまま待ち時間になる。実測で委譲1回あたり約1〜3分を要している。
>
> 「一括生成してはならない」（DR-2 冒頭）は**順序**の規約であって、**委譲回数**の規約ではない。
> 1回の委譲の中で `briefing.md` → `requirements.md` の順に作れば、規約は守られる。
> **委譲の中でも、前の成果物を読んでから次を書くこと。**

**初回**は `{{OUTPUT_DIR}}/` をディレクトリごと新規作成し、`briefing.md` を生成する。

**2回目以降（`briefing.md` が既に存在する場合）は継続モードとする。**
前回の成果物を読み、新しい入力との**差分だけを更新**する。全部を作り直してはならない。
変わっていない箇所を再生成すると、前回お客様と合意した表現が理由なく変わる。

- 入力は Figma MCP 経由の `FIGJAM_URL`。MCP が使えない場合は `RAW_HEARING_MEMO` へ即座にフォールバックする
- **MCP の接続で立ち止まらない。** 2回失敗したらフォールバックへ切り替える
- 実データは §4 のガードレールに従いマスクする

### DR-1b. 上流スキャン（オーケストレータ）

`product-agent` の委譲が返ったら、**下流へ渡す前に** S-5 を走らせる。

```
python3 scripts/check_upload_safety.py <OUTPUT_DIR>
```

**上流で止めれば1箇所の修正で済む。** 下流へ流れてから気づくと、転記先すべてを直すことになる。
実測でも `requirements.md` に `briefing.md` 参照が3件残っていた事例が発生している。

### DR-2. 最小仕様の生成（`design-agent` へ**1回だけ**委譲）

> **一括生成してはならない。** 各ドキュメントは直前の成果物を入力とする。
> ただし DRAFT では各成果物の**深さを絞る**（下表の「DRAFT で書くこと」に限定する）。
>
> **これは1回の委譲の中で行う。** `design-agent` を成果物ごとに呼び直さない。
> 委譲時に、下表の「DRAFT で書くこと」と**行数の目安を必ず伝えること**。
> 1回の出力が大きくなるぶん、分量規律が緩みやすい。**成果物を1つ書くごとに自己点検を通す。**

| 順 | 成果物 | 担当 | DRAFT で書くこと | ITERATE で補完すること |
|---|---|---|---|---|
| ① | `requirements.md` | `product-agent` | **利用文脈 C-1〜C-5**、Must Have、Open Questions | Should/Could/Won't、データ構造、非機能要件の詳細 |
| ② | `design.md` | `design-agent` | **D-00 支配的判断の特定** ＋ 支配的なモデルの ADR（D-01/D-02 等） | D-03 情報設計 / D-04 技術構成、例外制御フロー、状態遷移図 |
| ②b | `screens.md` | `design-agent` | **D-00 で「要」のときのみ**。画面一覧／遷移図（Mermaid）／表示要素／アクション／**空状態と条件分岐** | 網羅的な要素定義、詳細仕様 |
| ②c | `content.md` | `design-agent` | **コンテンツ駆動型のときのみ**。画面に出る**実際の文言**（仮説として明記） | 全画面ぶんの網羅、妥当性検証後の確定版 |
| ③ | `Guidelines.md` | `design-agent` | カラートークン、書体、**変更要求→トークン写像表** | 禁則事項の全文、モーション規約、禁止識別子リスト |
| ④ | `figma_make_prompt.md` | `design-agent` | Task/Context/Elements/Behavior/Constraints 一式 | ― |

- **C-1〜C-5、D-00、写像表の3つは DRAFT でも省略不可。** これらが後続の反復速度を決めるため
- **決定モデルを機械的に全部回さない。** D-00 で非支配的と判定したものは、既定値の採用を1〜2行で述べるに留める。
  情報が無いところから1節かけて結論を出すのは、導出ではなく儀式である
- **画面が2枚以上、または情報設計が支配的なら `screens.md` を作る。**
  これが無いと `figma_make_prompt.md` の Elements 節が書けない
- **コンテンツ駆動型（画面から文字を消すと何も残らない）なら `content.md` を作る。**
  無いと Figma Make がダミーテキストで埋め、製品として何も伝わらないものになる
- `figma_make_prompt.md` には **「ダミーテキストでの生成を禁止する」** の一文を必ず含める
- C-3（装置）／C-4（物理環境）が欠けている場合、**推測で埋めてその場で口頭確認する**（止まらない）
- 各成果物の詳細規約は、担当エージェントの定義と `.claude/knowledge/` に従う

### DR-2b. advisory スキャン（オーケストレータが自ら実行する）

DR-2 の直後、**サブエージェントへ委譲せず**オーケストレータ自身が走査する。
`quality-agent` を起動するとコールドスタートで1〜2分失うため、DRAFT では呼ばない。
フル検査（V-1〜V-4）は ITERATE パスで `quality-agent` が行う。

| # | 検査 | 見るもの | 検出時 |
|---|---|---|---|
| S-1 | **解法の混入** | `briefing.md` / `requirements.md` に配色・レイアウト・技術構成の**指定**が無いか。あれば D-01/D-02 が「導出」ではなく「追認」になっている | 保留＋冒頭に警告 |
| S-2 | **機密の平文** | 実URL・アクセスキー・個人が特定される記述が残っていないか | 保留＋冒頭に警告 |
| S-3 | **DOM バインド** | `figma_make_prompt.md` の Constraints に禁止識別子リストが転記されているか | 保留 |
| S-4 | **C-3 / C-4 の欠落** | `requirements.md` の装置・物理環境が空でないか | 保留 |
| S-5 | **アップロード安全性** | アップロードする5点に、生の発言引用・`briefing.md` 参照・実URL・資格情報が残っていないか | **保留にせず、その場で直す** |

**S-5 はスクリプトで判定する。目視しない。**

```
python3 scripts/check_upload_safety.py <OUTPUT_DIR>
```

> **S-5 だけが例外である理由。**
> 他の4件は保留にしても、失われるのは精度だけである。S-5 は違う。
> 保留のまま Figma Make へ上げれば、**お客様の発言がその瞬間に外部サービスへ渡り、取り消せない**。
> 止まらないことと、送ってしまうことは別である。由来を識別子へ置換すれば数十秒で済む。

検出したものは `review_history.md` の `## 保留指摘（DRAFT）` へ追記する。

**検出が0件でも `review_history.md` を作成し、「保留指摘なし」と明記する。**
ファイルが無いと、検査したのか、検査して0件だったのかが区別できない。
`figma_output/` の空ディレクトリと同じで、**記録が無いこと自体を記録にしてはならない。**

> ⚠️ **時間がないことは、検査を省略する理由にならない。**
> 止めないだけであって、見ないわけではない。

### DR-3. 顧客反復（Figma Make ループ）

`figma_make_prompt.md` を Figma Make へ投入し、プロトタイプをお客様に提示する。

修正依頼は感覚で処理せず、**`Guidelines.md` の「変更要求 → トークン写像表」を経由**して
トークンの操作へ変換する。写像表に無い要求が出たら、その場で写像表に追記する。

**反復のたびに、`review_history.md` へ速記で追記する。**

```markdown
## 顧客反復ログ

| # | お客様の言葉 | 写像先 |
|---|---|---|
| 1 | 「もう少し明るく」 | 背景トークン |
```

> **DRAFT 中は2列だけでよい。** 時刻・所要時間・上流への影響は ITERATE パスで埋める。
> 記録がスピードを殺してはならない。

### DR-3 の最後 ―― 最終出力の回収（省略不可）

商談が終わったら、**Figma Make の最終出力を回収して保存する。**

```
{{OUTPUT_DIR}}/figma_output/     コード（推奨）またはスクリーンショット
```

**`/log` は伝票であって実物ではない。** Figma Make は依頼以上のことをしたり、
異なる解釈をしたりする。実物を回収しないと、以下が検出できない。

- **記録漏れ** ―― ログに無い変更が画面に入っている
- **仕様との乖離** ―― `Guidelines.md` のトークンと、実際に使われた値が違う

コードが取得できる場合はコードを保存する。トークン値を機械的に突き合わせられるため、
スクリーンショットより検出精度が高い。

## ■ ITERATE パス ―― 商談後（自分の机で）

> ここからは **blocking**。`FAIL` があれば停止し、差し戻す。時間制限はない。
>
> ⚠️ **ITERATE は「検証と補完」のパスであり、「生成」のパスではない。**
> `OUTPUT_DIR` に DRAFT の成果物（`briefing.md` / `requirements.md`）が無い場合は、
> **成果物を新規生成せず、停止して `/draft` の実行を促すこと。**
> DRAFT を飛ばすと、分量制限も advisory スキャンも、
> そして**顧客反復で入るはずだったお客様の声**も、すべて失われる。

### IT-1. 検証ゲートと上流補完（`quality-agent` → 各担当）

> **最初に、回収した最終出力と `/log` の伝票を突き合わせる。**
> 実物を見ずに伝票だけで仕様を書き換えると、仕様と画面が別々にズレていく。

1. **反復ログの補完**：`## 顧客反復ログ` に、時刻・所要時間・上流への反映内容を追記して完成させる
2. **仕様変更の上流反映**：反復で確定した変更が上流と矛盾する場合、**下流ではなく上流を更新**する（§4 整合性の優先順位）
3. **保留指摘の消化**：`## 保留指摘（DRAFT）` に溜めた指摘を1件ずつ判定する
4. **検証ゲート1・2 の実行**：`verification-protocol.md` に従い、以下を走査する
   - ゲート1: 利用文脈の抽出漏れ（特に C-3 / C-4）、内部矛盾、解法の混入、機密の混入
   - ゲート2: V-1 矛盾／V-2 トレーサビリティ断絶／V-3 孤児成果物／V-4 用語・値の揺れ
   - 重点: セキュリティ要件の貫通、DOM バインド規約の貫通、**D-01/D-02 が C-1〜C-5 まで遡れるか**
5. **DR-2 で省いた項目の補完**：上表「ITERATE で補完すること」を各担当エージェントが埋める
6. **完成度を上げる成果物の追加**（必要に応じて。DRAFT では作らない）
   - `detailed_spec.md` ―― 画面遷移ロジック、イベント、状態変化、空状態の網羅
   - `user_story.md` / `acceptance.md` ―― 受入基準の形式化
   - `content.md` の妥当性検証と確定版への更新（DRAFT 版は仮説である）
7. **開放的レビュー（枠を1つだけ設ける）**
   1〜6 は**閉じた問い**であり、尋ねると決めたことしか見つけない。最後に一度だけ、
   `quality-agent` へ**枠のない問い**を投げる ―― 「V-1〜V-4 でも保留指摘でもない観点で、
   最も改善効果が大きいものを3つ挙げよ」。**採否は判断する。全部拾うと過剰設計になる。**
   商談中（DRAFT）ではやらない。時間があるのはこのパスだけである
8. **記録と停止**：結果を `review_history.md` へ追記し、人間のサインオフを待って停止する

## ■ スコープ外 ―― 実装

**本フレームワークの範囲は、確定した仕様と、動くプロトタイプまでである。**
本実装（本番コードの記述）は含まない。

これは能力の欠落ではなく、**線を引いた結果**である。理由は2つある。

1. **商談で見せた画面は Figma Make が生成している。** それを捨てて別実装を起こすと、
   お客様が合意した画面と実装物が別々に育つ。整合を取る仕組みが要り、速度の利点が消える
2. **仕様と画面が揃った時点で、実装チームへ渡せる。** そこから先は本フレームワークの問題ではなく、
   受け取る側の開発プロセスの問題である

したがって最終成果物は、**検証済みの仕様一式 ＋ 動くプロトタイプ ＋ 引き渡し資料**とする。

### 引き渡し資料（ITERATE の任意成果物）

実装を行わないが、**実装可能な単位に割ることまでは仕様側の責任**とする。
`quality-agent` が `delivery-planning.md` に従い `tasks.md` を生成する。

- Bolt 分解（最初は必ず Walking Skeleton）、依存順序、リスクの前倒し
- 各 Bolt に 機能・セキュリティ・UX・耐障害性 の4観点 DoD
- DoD は「実装した」ではなく「**何がどうなれば完了か**」を検証可能な文で書く

**これは実装計画ではなく、引き渡しのための分解である。** 実装の可否と工数は受け取る側が判断する。
