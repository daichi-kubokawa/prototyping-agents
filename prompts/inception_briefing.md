# 2. 本フレームワークの位置づけ

本プロンプトは、新規プロダクト【PROJECT_NAME】の開発において「仕様駆動開発（Spec-Driven Development）」のワークフローを厳格に回すための実行フレームワークです。

人間が定義した最上流のインプット（PROJECT_SUMMARY / FIGJAM_URL / RAW_HEARING_MEMO）を単一の真実のソース（SSoT）とし、そこから各ドキュメントを、`.claude/agents/` に定義された専門エージェントへコンテキストスイッチしながら、一切の矛盾なく自律展開します。

**本フレームワークはプロダクトに依存しません。** 深夜の暗室で使う記録アプリにも、屋外・日中の点検アプリにも、同一のフローで適用できます。特定のプロダクトの答え（配色・レイアウト・技術構成）を、本プロンプトに書き込んではなりません。

## 実行主体となるエージェント

| エージェント | 定義 | 担う成果物 |
|---|---|---|
| `product-agent` | AI Product Manager | `briefing.md` / `requirements.md` |
| `design-agent` | AI Technical Lead & UX Designer | `design.md` / `Guidelines.md` / `figma_make_prompt.md` |
| `quality-agent` | AI QA Lead & Technical Writer | `review_history.md` / `tasks.md` / `README.md` |

# 3. 最優先ガードレール（全フェーズ共通）

- **シークレット情報のマスク徹底**：
  生成するすべての Markdown において、`local_env.json` からバインドした生データ（`FIGJAM_URL`、アクセスキー、プライベートパス、個人が特定される生ヒアリング内容）を平文出力してはなりません。必ず `[FigJam Board (Confidential)]` `[Confidential]` 等にマスクし、Git 公開時の漏洩リスクを物理的に遮断してください。

- **層の厳守（要件と解法の分離）**：
  上流ドキュメントに技術的解法を書いてはなりません。書くべきは目的と制約です。
  「単一 HTML で実装する」ではなく「ビルド工程なしで配布でき、開くだけで起動できること」と書きます。
  解法の決定は `design.md` の ADR の役割であり、それを上流で先取りすると設計判断が消滅します。

- **仕様の一貫性担保**：
  `briefing.md` を SSoT とし、下流ドキュメントは必ずここに記述された課題・利用文脈・設計の狙いに準拠し、根拠を持ってください。

- **推測・不足情報の可視化**：
  - `briefing.md` に存在しない情報を、下流で確定事項として補完してはなりません
  - 推測が必要な場合は「Assumptions（前提・推測）」として明示してください
  - 不足している重要情報は「Open Questions（要確認事項）」として列挙してください

- **整合性の優先順位**：
  仕様間で矛盾や競合が発生した場合の優先順位は以下とします。

  1. `briefing.md`（最上流）→ 2. `requirements.md` → 3. `design.md` → 4. `Guidelines.md`
  → 5. `figma_make_prompt.md` → 6. `tasks.md` → 7. `README.md`

- **言語規約**：
  思考プロセス、および出力するすべての Markdown・プロンプトは、洗練された日本語で統一してください。

# 4. ディレクトリ構成と役割分担

本リポジトリは、プロダクト非依存の**再利用層**と、案件固有の**案件層**の二層で構成されます。
**成果物はすべて `projects/{{PROJECT_SLUG}}/` 配下に生成してください。リポジトリ直下に生成してはなりません。**

```
.
├── .claude/agents/                    ── 再利用層：エージェント定義
│   ├── product-agent.md
│   ├── design-agent.md
│   └── quality-agent.md
│
├── prompts/                           ── 再利用層：ワークフロー定義
│   └── inception_briefing.md          ★本プロンプト（Prompt Ops 資産）
│
└── projects/{{PROJECT_SLUG}}/         ── 案件層：本実行の成果物
    ├── CLAUDE.md                      【手動配備】案件固有ルール・既知の利用文脈
    ├── briefing.md                    【フェーズ1】SSoT — Why & Who
    ├── review_history.md              【全フェーズ】レビュー履歴・サインオフ証跡（追記のみ）
    ├── requirements.md                【フェーズ2】product-agent — 利用文脈 C-1〜C-5、スコープ
    ├── design.md                      【フェーズ2】design-agent — ADR（D-01/D-02）、状態遷移図
    ├── Guidelines.md                  【フェーズ2】design-agent — デザイントークン、変更要求写像
    ├── figma_make_prompt.md           【フェーズ2】design-agent — Figma Make 連携プロンプト
    ├── tasks.md                       【フェーズ4】quality-agent — DoD 付き実装タスク
    ├── README.md                      【フェーズ4】quality-agent — 意思決定の解説
    └── index.html                     【フェーズ4】プロトタイプ本体
```

# 5. 実行ステップ

## 【フェーズ1：原点（briefing.md）構築 ➔ 検証ゲート1】

1. **環境変数のバインド**：
   Git 追跡外の `local_env.json` からプロジェクト設定パラメータを動的にバインドして実行します。本プロンプトに実データを直接上書き保存することは、シークレットリーク防止の観点から厳格に禁止します。

2. **原点の自律生成**（`product-agent`）：
   バインドされた設定変数をもとに Figma MCP を起動して【FIGJAM_URL】をパースし（MCP が利用できない場合は【RAW_HEARING_MEMO】を入力とする）、すべての設計判断の原点となる `projects/{{PROJECT_SLUG}}/briefing.md` を生成してください。実URL等は §3 のガードレールに従い厳重にマスクすること。

3. **【検証ゲート1】の実行**（`quality-agent`）：
   `briefing.md` の生成が完了したら、処理を止めずに自律的にレビューを行ってください。

   > ⚠️ **この時点で `design.md` も `Guidelines.md` も存在しません。** 実装レベルの事項（DOM バインド、タイムアウト制御、配色）を検査対象にしてはなりません。存在しない成果物への検査は、必ず「N/A（対象成果物が未生成）」と判定してください。

   検査観点は以下に限定します。

   - **利用文脈の抽出漏れ**: C-1（ユーザー）／C-2（タスク）／C-3（装置・入力方式）／C-4（物理環境）／C-5（社会的環境）の5変数が抽出されているか。**特に C-3 と C-4 の欠落は、下流の設計判断を機能不全にするため重大欠陥として扱う**
   - **内部矛盾**: `briefing.md` 内で相互に矛盾する記述がないか
   - **解法の混入**: ヒアリング段階の記述に、技術的解法が「確定事項」として紛れ込んでいないか
   - **機密の混入**: マスクされるべき実データが平文で残っていないか

4. **検証ゲート1 の記録**（`quality-agent`）：
   検証結果を `projects/{{PROJECT_SLUG}}/review_history.md` に、以下のセクション名で記録してください。

   `## 検証ゲート1: 上流ブリーフ ➔ 要件定義への移行前レビュー`

   各検査項目には **`PASS` / `FAIL` / `N/A`** のいずれかを必ず付し、`FAIL` の場合は差し戻し先と修正対策案を記載してください。末尾に人間のレビューコメント用プレースホルダーを配置すること。

5. **停止とサインオフ待機**：
   人間の最終レビューおよび手動サインオフを待つため、処理を完全に停止してください。

---

## 【フェーズ2：仕様の逐次展開 ➔ 検証ゲート2】

（※人間からレビューフィードバックを受け取り、サインオフの合意が得られた後に実行します）

1. **フィードバックのバインド**：
   人間から受け取った修正指摘、および合意した設計の狙いを `review_history.md` の「人間のコメント」プレースホルダーに記録・同期してください。

2. **下流仕様の逐次生成**：

   > ⚠️ **一括生成してはなりません。** 各ドキュメントは直前の成果物を入力として参照するため、以下の順序で**逐次**生成し、各ステップで前段の内容を実際に読み込んでから次へ進んでください。

   | 順 | 成果物 | 担当 | 入力 | 必須要件 |
   |---|---|---|---|---|
   | ① | `requirements.md` | `product-agent` | `briefing.md` | 利用文脈 C-1〜C-5、MoSCoW（`Won't Have` 空欄禁止）、非機能要件、Assumptions / Open Questions |
   | ② | `design.md` | `design-agent` | ①  | **ADR D-01（輝度極性）／D-02（操作アンカー）を必須**。決定・根拠引用・導出プロセス・棄却案・再検討トリガの5点セット。中核ロジックのインターフェースと例外制御、Mermaid `stateDiagram-v2` による状態遷移図、DOM バインド規約 |
   | ③ | `Guidelines.md` | `design-agent` | ①② | 禁則事項（AI slop 排除）、カラートークン（コントラスト比実測値を併記）、書体選定の論証、スペーシング、モーション規約、**変更要求 → トークン写像表**、grep 可能な禁止識別子リスト |
   | ④ | `figma_make_prompt.md` | `design-agent` | ②③ | Figma Make 構造（Task / Context / Elements / Behavior / Constraints）に準拠。**Constraints 節に禁則事項と DOM バインド規約を必ず転記**すること |

   各成果物の詳細な生成規約は、担当エージェントの定義（`.claude/agents/*.md`）に従ってください。本プロンプトに具体値を書いてはなりません。

3. **【検証ゲート2】仕様間クロスレビューの実行**（`quality-agent`）：
   生成完了直後、各仕様書間の論理的一貫性を全件走査してください。検査は以下の4種別で行います。

   - **V-1 矛盾**: 上流が禁止した事項を下流が採用していないか。特に、要件のセキュリティ・ライフサイクル要件と矛盾する記述が設計側に**1文字でも**混入していないか
   - **V-2 トレーサビリティ断絶**: **D-01 / D-02 が、`requirements.md` の C-1〜C-5 のどの記述に由来するか照合できるか。** 根拠・棄却案・再検討トリガのいずれかが欠落した ADR は不合格として差し戻す
   - **V-3 孤児成果物**: 要件にあって設計にない項目（欠落）／設計にあって要件にない項目（スコープクリープ）
   - **V-4 用語・値の揺れ**: 同一のトークン名・寸法・状態名が、文書間で異なる値を持っていないか

   あわせて、`innerHTML` 系の危険なバインドを許容する記述が設計側に残っていないこと、および禁止識別子リストが明記されていることを確認してください。

4. **検証ゲート2 の記録**（`quality-agent`）：
   `review_history.md` の下部に、以下のセクション名で**追記（アペンド）**してください。既存の記録を上書き・削除してはなりません。

   `## 検証ゲート2: 下流仕様・設計の相互整合性レビュー`

5. **停止とサインオフ待機**：
   人間の最終サインオフを待つため、処理を完全に停止してください。

---

## 【フェーズ3：顧客との反復（Figma Make ループ）】

（※このフェーズは人間が主導します。AI は求められたときに応答してください）

1. **プロトタイプ生成**：
   `figma_make_prompt.md` を Figma Make へ投入し、動作プロトタイプを生成します。

2. **顧客への提示と改善の反復**：
   お客様に提示し、その場でフィードバックを受けて修正・再提示します。

   > 修正依頼は感覚で処理せず、**`Guidelines.md` の「変更要求 → トークン写像表」を経由**して、トークンの操作へ変換してください。これにより、3回目以降の修正でもデザインシステムの一貫性が崩れません。
   > 写像表に無い要求が出た場合は、その場で写像表に追記してください。

3. **反復結果の反映**：
   反復によって確定した仕様変更を、`review_history.md` に以下のセクション名で追記してください。

   `## フェーズ3: 顧客反復による仕様変更ログ`

   変更が `requirements.md` や `design.md` の記述と矛盾する場合は、**下流ではなく上流を更新**してください（§3 整合性の優先順位に従う）。

4. **収束の判定**：
   お客様との合意が得られ、仕様変更が収束したことを人間が判断した時点で、フェーズ4へ進みます。

---

## 【フェーズ4：実装計画と実装 ➔ 検証ゲート3】

> ⚠️ **`tasks.md` はこのフェーズで生成します。** フェーズ2で生成すると、フェーズ3の顧客反復によって陳腐化するためです。実装計画は、仕様が固まってから立てます。

1. **実装計画の生成**（`quality-agent`）：
   反復後の確定仕様をもとに `tasks.md` を生成してください。

   - 実装単位（Bolt）への分解と依存関係。**最初の Bolt は必ず Walking Skeleton**（端から端まで貫通する最小構成）とし、各 Bolt は垂直スライスであること
   - リスクの高い要素（技術的不確実性、外部連携）を早い Bolt に前倒しすること
   - 各 Bolt に **機能・セキュリティ・UX・耐障害性**の4観点の DoD チェックリストを定義すること。DoD は「実装した」ではなく「**何がどうなれば完了か**」を検証可能な文で書くこと

2. **実装**：
   `design.md` `Guidelines.md` `tasks.md` を入力として `projects/{{PROJECT_SLUG}}/index.html` を実装してください。

3. **【検証ゲート3】DoD 検証**（`quality-agent`）：
   実装結果を `tasks.md` の DoD に照合し、各項目に `PASS` / `FAIL` を付して判定してください。あわせて禁止識別子リストによる静的チェックを実行してください。

4. **意思決定のドキュメント化**（`quality-agent`）：
   `README.md` を生成してください。技術構成の選定理由は `design.md` の ADR に**由来していなければなりません**。ADR が存在しない決定を README で創作してはなりません。

5. **検証ゲート3 の記録と停止**：
   `review_history.md` に `## 検証ゲート3: 実装 DoD 検証` を追記し、人間の最終確認を待って停止してください。
