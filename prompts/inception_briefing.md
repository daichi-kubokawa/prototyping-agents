# 1. 実行パラメータ

値は `local_env.json`（Git 追跡外）からバインドする。
**本ファイルに実データを書き込んではならない**（シークレットリーク防止）。

```
MODE              DRAFT | ITERATE | BUILD  実行モード（§2）
PROJECT_NAME      文字列                   プロダクト名
OUTPUT_DIR        相対パス                 成果物の出力先ディレクトリ
PROJECT_SUMMARY   文字列                   一行概要
FIGJAM_URL        URL                     ヒアリング整理先（Figma MCP 経由で取得）
RAW_HEARING_MEMO  文字列 or ファイルパス      FigJam が使えないときの入力
```

- `MODE` はコマンド（`/draft` `/iterate` `/build`）が設定する。`local_env.json` には不要
- `RAW_HEARING_MEMO` は `$ARGUMENTS`（コマンドの引数）で上書きされる。**引数が優先**
- `OUTPUT_DIR` が未設定だと出力先が決まらず実行できない

### `OUTPUT_DIR` の決め方

本リポジトリは**雛形と実演を同居させる**ため、案件ごとにサブディレクトリを切る。
実案件では **1リポジトリ = 1案件**とし、リポジトリ直下に近い場所へ出力する。

```
examples/<案件名>    本リポジトリ（複数の実演を並べて比較するため）
spec                 実案件（Template から生成した専用リポジトリ）
```

# 2. 二周構造 ―― DRAFT パスと ITERATE パス

本フレームワークは、**同じ成果物を2周**する。1周目は速く、2周目は堅く。
これは「簡易版」と「完全版」ではなく、**最適化する対象が違う2つの周回**である。

| | **DRAFT** | **ITERATE** |
|---|---|---|
| **いつ** | 商談中（お客様の目の前） | 商談後（自分の机） |
| **最適化対象** | 画面に到達するまでの時間 | 論理的無矛盾とトレーサビリティ |
| **検証ゲート** | **advisory** ―― 記録するが停止しない | **blocking** ―― FAIL なら停止・差し戻し |
| **人間の停止** | **なし**（喋っているため物理的に不可能） | 各ゲート後にサインオフ待ち |
| **生成物** | `briefing` / `requirements`（最小）/ `design`（D-01・D-02のみ）/ `Guidelines` / `figma_make_prompt` | 上記の検証と補完。`detailed_spec` 等の追加 |
| **目標時間** | 画面到達まで8分以内 | 制限なし |

**実装（BUILD）は、この2周の外側にある。**
DRAFT と ITERATE は同じ成果物を2周するが、BUILD は**その成果物を消費して別のもの（`index.html`）を作る**。
性質が違うため、コマンドを分けている。

```
仕様パス（同じ成果物を2周）    /draft  →  /iterate
その後の実装（成果物を消費）    /build
```

> **なぜ分けるのか**
> 検証ゲートでサインオフする人間は、あなた自身である。そしてお客様の前で、あなたは喋っている。
> レビューは物理的に不可能であり、そこで止まるのはお客様の時間を捨てているだけである。
> **ゲートは商談中に回すものではなく、商談と商談の「あいだ」で回すもの。**
> こうすることで、商談中は速く、商談後は堅く、次の商談は前回より精度が高い状態で始まる。

**DRAFT で作った成果物を、ITERATE で検証・補完する。捨てる作業は一切ない。**

# 3. 本フレームワークの位置づけ

人間が定義した最上流のインプット（PROJECT_SUMMARY / FIGJAM_URL / RAW_HEARING_MEMO）を SSoT とし、
`.claude/agents/` に定義された専門エージェントへコンテキストスイッチしながら仕様を展開する。

**本フレームワークはプロダクトに依存しない。** 深夜の暗室で使う記録アプリにも、屋外・日中の点検アプリにも、
同一のフローで適用できる。特定プロダクトの答え（配色・レイアウト・技術構成）を本プロンプトに書いてはならない。

| エージェント | 定義 | 担う成果物 |
|---|---|---|
| `product-agent` | AI Product Manager | `briefing.md` / `requirements.md` |
| `design-agent` | AI Technical Lead & UX Designer | `design.md` / `Guidelines.md` / `figma_make_prompt.md` |
| `quality-agent` | AI QA Lead & Technical Writer | `review_history.md` / `tasks.md` / `README.md` |

# 4. 最優先ガードレール（全モード共通）

**モードによって緩めてよいのは「停止するかどうか」だけである。以下はDRAFTでも一切緩まない。**

- **シークレット情報のマスク徹底**：
  `local_env.json` からバインドした生データ（`FIGJAM_URL`、アクセスキー、プライベートパス、
  個人が特定される生ヒアリング内容）を平文出力してはならない。必ず `[Confidential]` 等へマスクする。

- **層の厳守（要件と解法の分離）**：
  上流ドキュメントに技術的解法を書かない。書くのは目的と制約である。
  「単一 HTML で実装する」ではなく「ビルド工程なしで配布でき、開くだけで起動できること」。

- **DOM バインド規約**：
  `innerHTML` 系の禁止と `textContent` / `createElement` 規約は、DRAFT でも省略しない。
  速度のために安全性を落とさない。

- **推測・不足情報の可視化**：
  上流に存在しない情報を、下流で確定事項として捏造しない。
  推測は **Assumptions**、不足は **Open Questions** として明示する。

- **案件層はゼロから生成される**：
  `{{OUTPUT_DIR}}/` は実行時に新規作成する。実行前にこの配下へ何かを置いてはならない。

- **整合性の優先順位**：
  1. `briefing.md` → 2. `requirements.md` → 3. `design.md` → 4. `Guidelines.md`
  → 5. `figma_make_prompt.md` → 6. `tasks.md` → 7. `README.md`

- **言語規約**：思考プロセスと出力するすべての Markdown は、洗練された日本語で統一する。

# 6. 実行ステップ

## ■ DRAFT パス ―― 商談中（目標: 8分で画面へ）

> このパスでは **一切停止しない。** 検証は advisory であり、指摘は `review_history.md` の
> `## 保留指摘（DRAFT）` へ溜めるだけにする。差し戻しも再生成も行わない。
> 判断はすべて ITERATE パスに繰り延べる。

### DR-1. 原点構築（`product-agent`）

`{{OUTPUT_DIR}}/` をディレクトリごと新規作成し、`briefing.md` を生成する。

- 入力は Figma MCP 経由の `FIGJAM_URL`。MCP が使えない場合は `RAW_HEARING_MEMO` へ即座にフォールバックする
- **MCP の接続で立ち止まらない。** 2回失敗したらフォールバックへ切り替える
- 実データは §4 のガードレールに従いマスクする

### DR-2. 最小仕様の生成（逐次）

> **一括生成してはならない。** 各ドキュメントは直前の成果物を入力とする。
> ただし DRAFT では各成果物の**深さを絞る**（下表の「DRAFT で書くこと」に限定する）。

| 順 | 成果物 | 担当 | DRAFT で書くこと | ITERATE で補完すること |
|---|---|---|---|---|
| ① | `requirements.md` | `product-agent` | **利用文脈 C-1〜C-5**、Must Have、Open Questions | Should/Could/Won't、データ構造、非機能要件の詳細 |
| ② | `design.md` | `design-agent` | **D-00 支配的判断の特定** ＋ 支配的なモデルの ADR（D-01/D-02 等） | D-03 以降、例外制御フロー、状態遷移図、ユニット分解 |
| ②b | `screens.md` | `design-agent` | **D-00 で「要」のときのみ**。画面一覧／遷移図（Mermaid）／表示要素／アクション／**空状態と条件分岐** | 網羅的な要素定義、詳細仕様 |
| ②c | `content.md` | `design-agent` | **コンテンツ駆動型のときのみ**。画面に出る**実際の文言**（仮説として明記） | 全画面ぶんの網羅、妥当性検証後の確定版 |
| ③ | `Guidelines.md` | `design-agent` | カラートークン、書体、**変更要求→トークン写像表** | 禁則事項の全文、モーション規約、禁止識別子リスト |
| ④ | `figma_make_prompt.md` | `design-agent` | Task/Context/Elements/Behavior/Constraints 一式 | ― |

- **C-1〜C-5、D-00、写像表の3つは DRAFT でも省略不可。** これらが後続の反復速度を決めるため
- **決定モデルを機械的に全部回さない。** D-00 で非支配的と判定したものは、既定値の採用を1〜2行で述べるに留める。
  情報が無いところから1節かけて結論を出すのは、導出ではなく儀式である
- **画面が2枚以上、または情報設計が支配的なら `screens.md` を作る。**
  これが無いと `figma_make_prompt.md` の Elements 節が書けない
- **コンテンツ駆動型（画面から文字を消すと何も残らない）なら `content.md` を作る。**
  無いと Figma Make がダミーテキストで埋め、製品として何も伝わらないものになる
- `figma_make_prompt.md` には **「ダミーテキストでの生成を禁止する」** の一文を必ず含める
- C-3（装置）／C-4（物理環境）が欠けている場合、**推測で埋めてその場で口頭確認する**（止まらない）
- 各成果物の詳細規約は、担当エージェントの定義と `.claude/knowledge/` に従う

### DR-3. 顧客反復（Figma Make ループ）

`figma_make_prompt.md` を Figma Make へ投入し、プロトタイプをお客様に提示する。

修正依頼は感覚で処理せず、**`Guidelines.md` の「変更要求 → トークン写像表」を経由**して
トークンの操作へ変換する。写像表に無い要求が出たら、その場で写像表に追記する。

**反復のたびに、`review_history.md` へ速記で追記する。**

```markdown
## 顧客反復ログ

| # | お客様の言葉 | 写像先 |
|---|---|---|
| 1 | 「もう少し明るく」 | 背景トークン |
```

> **DRAFT 中は2列だけでよい。** 時刻・所要時間・上流への影響は ITERATE パスで埋める。
> 記録がスピードを殺してはならない。

---

## ■ ITERATE パス ―― 商談後（自分の机で）

> ここからは **blocking**。`FAIL` があれば停止し、差し戻す。時間制限はない。
>
> ⚠️ **ITERATE は「検証と補完」のパスであり、「生成」のパスではない。**
> `OUTPUT_DIR` に DRAFT の成果物（`briefing.md` / `requirements.md`）が無い場合は、
> **成果物を新規生成せず、停止して `/draft` の実行を促すこと。**
> DRAFT を飛ばすと、分量制限も advisory スキャンも、
> そして**顧客反復で入るはずだったお客様の声**も、すべて失われる。

### IT-1. 検証ゲートと上流補完（`quality-agent` → 各担当）

1. **反復ログの補完**：`## 顧客反復ログ` に、時刻・所要時間・上流への反映内容を追記して完成させる
2. **仕様変更の上流反映**：反復で確定した変更が上流と矛盾する場合、**下流ではなく上流を更新**する（§4 整合性の優先順位）
3. **保留指摘の消化**：`## 保留指摘（DRAFT）` に溜めた指摘を1件ずつ判定する
4. **検証ゲート1・2 の実行**：`verification-protocol.md` に従い、以下を走査する
   - ゲート1: 利用文脈の抽出漏れ（特に C-3 / C-4）、内部矛盾、解法の混入、機密の混入
   - ゲート2: V-1 矛盾／V-2 トレーサビリティ断絶／V-3 孤児成果物／V-4 用語・値の揺れ
   - 重点: セキュリティ要件の貫通、DOM バインド規約の貫通、**D-01/D-02 が C-1〜C-5 まで遡れるか**
5. **DR-2 で省いた項目の補完**：上表「ITERATE で補完すること」を各担当エージェントが埋める
6. **完成度を上げる成果物の追加**（必要に応じて。DRAFT では作らない）
   - `detailed_spec.md` ―― 画面遷移ロジック、イベント、状態変化、空状態の網羅
   - `user_story.md` / `acceptance.md` ―― 受入基準の形式化
   - `content.md` の妥当性検証と確定版への更新（DRAFT 版は仮説である）
7. **記録と停止**：結果を `review_history.md` へ追記し、人間のサインオフを待って停止する

---

## ■ BUILD パス ―― 確定した仕様を消費する

> **BUILD は仕様を消費するパスである。** 検証ゲート1・2 に未解消の `FAIL` がある状態では実行しない。
> 仕様の欠陥はコードの欠陥より安く直せる。順序を飛ばさないこと。

### BD-1. 実装計画と実装（`quality-agent` → 実装）

1. **`tasks.md` の生成**：Bolt 分解（最初は必ず Walking Skeleton）、依存 DAG、
   機能・セキュリティ・UX・耐障害性の4観点 DoD。詳細は `delivery-planning.md` に従う
2. **実装**：`design.md` / `Guidelines.md` / `tasks.md` を入力として `index.html` を実装する
3. **検証ゲート3**：DoD 各項目に `PASS` / `FAIL` を付し、禁止識別子リストで静的チェックを実行する
4. **`README.md` の生成**：技術構成の選定理由は `design.md` の ADR に由来していなければならない
5. **記録と停止**：`review_history.md` へ追記し、人間の最終確認を待って停止する

# 7. `review_history.md` のセクション構成（固定）

表記が揺れると追記のたびに重複セクションが増えるため、以下で固定する。

```
## 保留指摘（DRAFT）                          ← DRAFT 中の advisory 指摘置き場
## 顧客反復ログ                                ← 改修依頼と対応（DRAFT で速記、ITERATE で補完）
## 検証ゲート1: 上流ブリーフ ➔ 要件定義への移行前レビュー
## 検証ゲート2: 下流仕様・設計の相互整合性レビュー
## 検証ゲート3: 実装 DoD 検証
```

各セクションには**検査項目・判定（PASS / FAIL / N/A）・根拠となる該当箇所の引用・修正対策案**を記録し、
末尾に人間のレビューコメント用プレースホルダーを配置する。
再現性のため、レビュー日時と対象コミットも併記する。**追記のみとし、過去の記録を書き換えてはならない。**
